## 1. Summary

Phase 4.7 ships **narrative documentation** as the **eighth content type** in the knowledge graph, alongside tutorials, learning journeys, blog posts, discovery missions, videos, api-docs, and code samples. This sub-phase is the **first with multiple sources feeding one entity**: `help.sap.com` (product help portal), `cap.cloud.sap` (CAP framework docs), and `ui5.sap.com` (UI5 Demo Kit) all flow into a single `HelpDocs` entity distinguished by a `source` column.

Each docs page becomes a graph node connected to concepts via a new `explains` predicate — semantically distinct from `officialReferenceFor` (Phase 4.5's api.sap.com signatures). Where api-docs answer "what is the signature?", help-docs answer "how does this work?".

The architecture lifts the Phase 4 chassis verbatim — schema shape, merge-on-write (#707), crash-safety gate (#708), variadic neighborhood merge, shared IRI registry, GC iteration, telemetry conventions, `JOB_REGISTRY` chassis (#756) — with **six structural deltas** from prior sub-phases:

1. **Three-source fanout into one entity.** Single `HelpDocs` entity with `source` discriminator column (`'help-sap-com' | 'cap-cloud-sap' | 'ui5-sap-com'`). First multi-source sub-phase; introduces cross-source dedupe at the fetch-time orchestrator.
2. **Three-fetcher-plus-orchestrator layout.** `srv/lib/help-docs/{help-sap-com-fetcher,cap-cloud-sap-fetcher,ui5-sap-com-fetcher,index}.js`. Each fetcher isolates one source's discovery mechanism; the orchestrator merges + dedupes.
3. **Optional anchor on link entity.** `HelpDocConceptLinks.anchor` is an optional slug-format H2/H3 identifier. Narrative docs have deep pages; per-concept anchors let users land at the right section rather than the page top.
4. **New concept-page section position — #3.** "Docs explaining this concept" lands between Learning journeys (#2) and Blog posts (#4). Sections #3-#8 previously present shift down one slot. First sub-phase to insert in the middle of the section list rather than append.
5. **Source badge on rendered rows.** Sidebar and concept-page rows include a compact source label (`SAP Help` / `CAP` / `UI5`) alongside the title, letting users assess canonicality at a glance.
6. **Cross-source contentHash dedupe with precedence `cap-cloud-sap > ui5-sap-com > help-sap-com`.** When help.sap.com mirrors a CAP or UI5 page, the framework-first source wins.

Weekly cron at `'17 5 * * 3'` (Wednesday 05:17 UTC, off-cluster). MAX-or-abort first-run gate; operator bootstraps via `scripts/seed-help-docs.cjs --commit` OR the new `seedHelpDocs()` admin action. Concept landing pages get section #3 "Docs explaining this concept". The tutorial-OP sidebar's "Other resources" widens to a 7-array merge.

**The #756 admin Cron health tile picks up the new `fetch-help-docs` cron automatically** via the `JOB_REGISTRY` chassis. Zero extra wiring; operator gets a Run-now button + JobLastRun history out of the box.

## 2. Scope

### Out of scope

- Per-section graph nodes. Phase 4.7 nodes are **whole pages only** (per §3 Q5). Section-level granularity would require HTML/markdown H2/H3 parsing in every fetcher and would break chassis uniformity by producing 5-10× the row count.
- Deep-crawl of help.sap.com beyond the hardcoded product-deliverable allowlist. New deliverables require a fetcher edit + redeploy — matches Phase 4.4/4.6 pattern for their scope constants.
- Anchor label mapping in the sidebar. Only the concept-page section renders anchor labels; the sidebar stays compact at `Title ↗ · <Source>` per §3 Q10.
- Iframe / modal rendering of docs pages. External links open in a new tab (`target="_blank"` + `rel="noopener"`). Matches Phase 4.5 Q12.
- Multi-language docs. English only. Other locales are legacy per project convention.
- Cross-org narrative docs (third-party SAP-focused blogs, community wikis, Medium/dev.to). Matches Phase 4 architecture spec's "out of scope (probably ever)" list.
- Backfill of help-doc data into Phase 4.1-4.6 entities (none needed — pure additive change).
- License / auth-scope badges on help-doc rows (help.sap.com pages are public by policy for the products in the allowlist).
- Retroactive DB-level dedupe. `contentHash` dedupe is a fetch-time filter, not a DB-side sweep. Prior-cycle rows with duplicate hashes are left as-is; the deterministic source-precedence rule ensures same-input-same-winner across cycles.

## 3. Architectural decisions (Q1-Q16)

Sixteen decisions resolved during brainstorming, with rationale:

| # | Decision | Rationale |
|---|---|---|
| Q1 | **One sub-phase, one entity, three fetchers** | Three narrative-doc sources answer the same user question ("how does X work?") and should render together on the concept page. A single entity + source discriminator keeps the chassis symmetric with all sibling sub-phases; three separate sub-phases (4.7a/b/c) would triple the chassis surface area without material user benefit. |
| Q2 | **Predicate `explains`** | Matches active-verb pattern of sibling predicates (`teaches`, `discusses`, `embodies`, `explains`, `officialReferenceFor`). Reads clearly in SPARQL: "the *CAP handlers* docs page **explains** the *cap-service-handlers* concept." Semantic distinction from `officialReferenceFor` (narrative vs reference) enables future authority-weighted ranking. |
| Q3 | **Cron-driven discovery, no YAML seed** | Sibling to Phase 4.4/4.6. Each source has a natural scope boundary (product allowlist, GitHub repo, Demo Kit index) enumerable by the fetcher. Zero curation cost; operator control via source-code edits to scope constants (matches `SAP_DEVELOPERS_CHANNEL_ID` and `const ORG = 'SAP-samples'` precedents). |
| Q4 | **help.sap.com scope: hardcoded product-deliverable pairs** | Same edit-latency as sibling scope constants. Seeded with ~20 developer-facing products drawn from the existing `HomepageShelves` CSV (already curated by the homepage team). Enumeration uses SAP's internal Vue-SPA API (`/http.svc/deliverableMetadata` + `/http.svc/pagecontent`) — verified live 2026-07-01 during Task 1 pre-flight. Rejected alternatives: sitemap.xml crawl (works but returns URLs only, no page bodies; would still need per-page pagecontent calls); scored HTML crawl (introduces a new heuristic dependency). Stability of the internal API is mitigated by non-fatal per-source failure + 540-day TTL — see §4.2.4a. |
| Q5 | **Page-level nodes + optional anchor on link entity** | Preserves chassis uniformity (one row per page). Anchor is optional slug-format identifier from H2/H3 of the doc page, extracted by the LLM. Users land at the concept-relevant section rather than the page top when the anchor is populated. Section-level nodes rejected as breaking chassis (5-10× node explosion). Page-level-only rejected as regressing UX on deep pages (Handlers.md ~800 lines). |
| Q6 | **Source discriminator column with UI badge** | `HelpDocs.source` column takes `'help-sap-com' \| 'cap-cloud-sap' \| 'ui5-sap-com'`. Sidebar and concept-page rows render short badge (`SAP Help` / `CAP` / `UI5`). Signals canonicality at a glance. Symmetric with Phase 4.6's `language` badge on Samples rows. |
| Q7 | **Section #3 — "Docs explaining this concept"** | Repositions the section list to promote authoritative narrative reference above supplementary discovery channels. New order: Tutorials → Journeys → **Docs** → Blogs → Missions → Videos → Reference → Samples → Prerequisites. First sub-phase to insert mid-list rather than append; requires re-ordering shifts of the 5 sections that follow. |
| Q8 | **Single weekly cron Wed 05:17 UTC (`'17 5 * * 3'`)** | Matches CAP docs' cadence (most volatile source); help.sap.com and UI5 refetches are `contentHash`-cache-short-circuited when pages haven't changed. Wednesday 05:17 avoids the existing :00/:13/:23/:43 cluster (samples Sun 04:43, videos Tue/Fri 04:23, api-docs 1st-of-month 04:23). Three-cron alternative rejected as tripling admin health tile surface area. |
| Q9 | **TTL 540 days** | Between blogs (540) and api-docs (1095) TTL bands. Narrative docs churn more than pure reference (cap.cloud.sap regularly renames pages during major version bumps); 540 days catches deletions within ~1.5 years while surviving multi-month cron outages. |
| Q10 | **Sidebar: `Title ↗ · <Source>`; concept page: `<badge> Title ↗ · <anchor label> · <snippet>`** | Sidebar stays tight (one line, seven content types competing for space). Concept page (more real estate) renders anchor label + one-line description snippet. Source badge everywhere; anchor label only where there's room. |
| Q11 | **LLM extraction: cap 8 concepts/page, floor 0.7, optional anchor** | Cap 8 (vs sibling 6) reflects narrative-docs density — a CAP Handlers page discusses 8-12 handler-related concepts. Floor 0.7 matches sibling extractors (LLM calibration is source-invariant). Anchor optional: LLM outputs null when concept is discussed throughout the page rather than in one section — prevents plausible-but-wrong anchor invention. |
| Q12 | **Three fetchers + orchestrator layout** | `srv/lib/help-docs/{help-sap-com-fetcher,cap-cloud-sap-fetcher,ui5-sap-com-fetcher,index}.js`. Isolates each source's discovery mechanism for independent testing (`_setMockFetcher` seam per source, matches Phase 4.6 pattern). Change-surface localized: UI5 Demo Kit URL changes touch one file only. Monolithic and no-orchestrator alternatives rejected. |
| Q13 | **`contentHash` dedupe with source precedence `cap-cloud-sap > ui5-sap-com > help-sap-com`** | Detects true content duplicates across sources regardless of URL/title. Precedence encodes canonicality: framework docs (CAP, UI5) win over the general help portal. Dupe drops log at INFO with `{ dupeOf, chosenSource, droppedSource }`. Title-fuzzy alternative rejected as producing false positives on distinct pages with similar names. |
| Q14 | **`/build/concepts` payload: cap 8, sort `source ASC, title ASC`; 7-array neighborhood merge** | Cap 8 matches LLM extraction cap. Alphabetical source sort puts `cap-cloud-sap` first, then `help-sap-com`, then `ui5-sap-com` — happens to match the precedence order and puts canonical framework docs at row 1 for concepts that pull from CAP. Neighborhood widens from 6 to 7 arrays; helper unchanged. |
| Q15 | **Test triad: full unit set (A) + hybrid full-cycle (B) + hybrid cascade-delete (C) + smoke concept-page (D) + smoke explore-data (E) + dedupe unit test (F)** | Matches Phase 4.6 test triad shape plus the dedupe unit test unique to this sub-phase's new multi-source risk. Cascade-delete extends the existing #789 audit (7 → 8 link tables). |
| Q16 | **Chassis defaults: 500 calls/cycle steady-state, MAX-or-abort first-run, three telemetry events, admin action via #756** | Same pattern as Phase 4.4/4.5/4.6 baseline. Steady-state weekly extractions typically 20-100/cycle (only `contentHash`-changed pages re-extract); 500 covers a big CAP release week. #756 chassis auto-provisions Run-now + JobLastRun. |

## 4. Architecture

### 4.1 Data model

Two new entities under namespace `com.sap.developers.ims.external` in `db/external-content.cds`:

```cds
// Phase 4.7 (#748): narrative documentation pages as graph nodes.
// Multi-source: help.sap.com + cap.cloud.sap + ui5.sap.com feed one entity.
// Spec: docs/superpowers/specs/2026-07-01-748-phase4.7-help-docs.md
entity HelpDocs : cuid, managed {
  slug              : String(150) @assert.unique;    // 'hd-<source>__<canonicalizedPath>'
  source            : String(20);                    // 'help-sap-com' | 'cap-cloud-sap' | 'ui5-sap-com'
  title             : String(255);
  description       : LargeString;                   // NCLOB — page body first ~2000 chars (see §10.1)
  url               : String(500);                   // canonical URL for the page
  sourceId          : String(200);                   // per-source stable identifier (URL path or GitHub blob path)
  contentHash       : String(64);                    // SHA-256(title+description+source+product+section)
  lastExtractedHash : String(64);                    // #708 crash-safety gate
  firstSeenAt       : Timestamp @cds.on.insert: $now;
  lastSeenAt        : Timestamp;
  pinUntil          : Timestamp;                     // chassis admin override

  // Help-doc-specific:
  product           : String(80);                    // help.sap.com product ID (e.g. 'btp', 'cap', 'hana-cloud'); 'cap' for cap-cloud-sap; 'ui5' for ui5-sap-com
  section           : String(120);                   // TOC parent section (help.sap.com only; null elsewhere)

  links             : Composition of many HelpDocConceptLinks on links.helpDoc = $self;
}

entity HelpDocConceptLinks : cuid, managed {
  helpDoc      : Association to HelpDocs @assert.notNull;
  concept      : Association to ims.Concepts @assert.notNull;
  predicate    : String(40);                         // 'explains'
  confidence   : Decimal(3, 2);                      // LLM floor 0.7
  anchor       : String(120);                        // optional H2/H3 slug; null-safe
  snippet      : String(200);                        // precomputed first ~120 chars of description for LOB-locator-safe payload reads (§4.7)
  extractedAt  : Timestamp;
  modelVersion : String(40);
}

annotate HelpDocConceptLinks with
  @assert.unique.helpDocConceptAnchor : [helpDoc, concept, predicate, anchor];
```

**Slug format:** `hd-<source>__<canonicalizedPath>` where `<source>` is one of `help-sap-com`, `cap-cloud-sap`, `ui5-sap-com` and `<canonicalizedPath>` lowercases, normalizes `/` to `__`, and replaces non-`[a-z0-9_]` chars with `_`. Examples:
- help.sap.com: `hd-help-sap-com__docs__btp__sap-business-technology-platform__getting-started`
- cap.cloud.sap: `hd-cap-cloud-sap__docs__node_js__handlers`
- ui5.sap.com: `hd-ui5-sap-com__topic__91f0652b6f4fc0cec4cb8d5b4a1e6e6d`

Slug is case-stable; equality checks use `LOWER(slug)`. Length ceiling 150 chars (higher than Phase 4.6's 120 because help.sap.com URLs are deep).

**`description: LargeString` (NCLOB)** — first ~2000 chars of page body (markdown-stripped for cap.cloud.sap and ui5.sap.com; HTML-stripped for help.sap.com). Same Phase 4.4/4.5/4.6 LOB-locator mitigation rule: never SELECT description alongside non-LOB metadata via CDS QL. Four read sites verified:
1. Cron upsert path: pulls only `ID/contentHash/lastExtractedHash`
2. `buildHelpDocTriples` in `kg-projection.js`: omits description
3. `published-concepts-query.js` payload: omits description (except one-line snippet if precomputed at write-time — see §4.7)
4. Neighborhood enrichment: omits description

**`@assert.unique.helpDocConceptAnchor : [helpDoc, concept, predicate, anchor]`** — includes `anchor` in the uniqueness tuple because the same concept can legitimately appear in two anchors on the same page (e.g. a concept discussed in both "Introduction" and "Advanced usage" sections). Null-anchor and non-null-anchor entries coexist; **HANA treats NULL as a distinct value in `UNIQUE` constraints**, so multiple `(helpDoc, concept, predicate, NULL)` rows would technically be allowed. The chassis relies on the extractor semantics — the LLM emits at most one `anchor: null` link per (helpDoc, concept, predicate) triple — plus the cron's "delete prior links, insert new set" upsert path (§4.4 step 3d) to prevent duplicates. Unit tests exercising the constraint run on the hybrid HANA path; the SQLite unit-test path uses a mock or per-test seed that respects the semantic contract.

**Discovery mechanism** (verified 2026-07-01 via live Playwright inspection):

help.sap.com is a Vue SPA that reads content from an internal `/http.svc/*` API. The Vue app itself is undocumented and load-balanced across `help.sap.com/docs/...` URLs, but the underlying API endpoints are stable and return JSON we can consume with native `fetch`.

Two-step per-deliverable walk:

1. **Deliverable metadata:** `GET https://help.sap.com/http.svc/deliverableMetadata?product_url=<product>&topic_url=<deliverable>&version=Cloud&deliverable_url=<deliverable>&language=en-US&state=PRODUCTION`
   Returns `{status: 'OK', data: {deliverable: {id, buildNo, ...}, topicLoio, filePath, ...}}`. The `deliverable.id` and `buildNo` are the primary keys used in step 2. `topicLoio` and `filePath` identify the landing page.

2. **Page content:** `GET https://help.sap.com/http.svc/pagecontent?deliverable_id=<id>&buildNo=<bn>&file_path=<filePath>`
   Returns `{status: 'OK', data: {deliverable: {fullToc: [...]}, body: '<html>...', currentPage: {...}}}`. The `fullToc` is the tree of all topics in the deliverable; `body` is the current-topic HTML.

**Enumeration algorithm:**

```javascript
// Pseudocode — Plan Task 1 §1.5 renders this to full JS
for (const { product, deliverable } of HELP_SAP_COM_DELIVERABLES) {
  const meta = await fetch(`.../deliverableMetadata?product_url=${product}&topic_url=${deliverable}&version=Cloud&deliverable_url=${deliverable}&language=en-US&state=PRODUCTION`);
  const { deliverable: { id, buildNo }, filePath } = meta.data;

  // First pagecontent call: landing page + fullToc
  const landing = await fetch(`.../pagecontent?deliverable_id=${id}&buildNo=${buildNo}&file_path=${filePath}`);
  const toc = landing.data.deliverable.fullToc;

  // Walk the TOC tree. Each node { t: title, u: file_path, c: children }.
  // Emit one HelpDocRow per topic. First topic (landing) uses the already-fetched body.
  for (const node of walkToc(toc)) {
    const body = (node.u === filePath) ? landing.data.body : await fetchPageContent(id, buildNo, node.u);
    yield buildRow({ product, deliverable, node, body });
  }
}
```

**Row construction:**

- `source = 'help-sap-com'`
- `sourceId = '<product>/<deliverable>/<file_path-without-.html>'` — stable across cycles
- `title = node.t` (the TOC entry title)
- `url = 'https://help.sap.com/docs/<product>/<deliverable>/<topicLoio-slug>?locale=en-US&state=PRODUCTION&version=Cloud'` — the human-readable URL (readableUrl mapping from metadata response)
- `description = stripHtml(body).slice(0, 2000).trim()` — plain text, first 2000 chars
- `product = product`
- `section = <parent-TOC-title if any, else null>` — the immediate parent in the `fullToc` walk
- `contentHash` computed by orchestrator (spec §4.2.5)

**Filter rules:**

- HTTP 200 required on both `deliverableMetadata` and `pagecontent` calls.

- `title = <text from index>`

- Stripped body length ≥ 200 chars.
- Title extractable and not empty.

#### 4.2.4a Stability note on internal `/http.svc/*` and `/docs/topics/*` endpoints

The help.sap.com `/http.svc/*` and ui5.sap.com `/docs/topics/*` endpoints are internal APIs consumed by SAP's own Vue SPAs. They are not part of any documented external contract, so SAP could change them without notice. Mitigations:

1. **Fetch failure per source is non-fatal** (spec §4.2.5). One source going 404 doesn't abort the cycle; the other two continue.
2. **Cron-health monitoring via #756 JOB_REGISTRY.** A silent multi-week outage surfaces on the admin Cron health tile.
3. **540-day TTL** (spec §5.1) means even a ~1.5-year outage doesn't empty the catalog immediately.
4. **v2 fallback path:** if help.sap.com's `/http.svc/*` gets deprecated, the sitemap.xml (`/http.svc/sitemapxml/sitemaps/sitemap_index.xml` — discovered via `robots.txt`) is a stable public alternative. If ui5.sap.com's `/docs/topics/*.html` breaks, the markdown source at `github.com/SAP-docs/sapui5` is a stable public alternative. Both fallbacks are more work but exist.

Non-mitigation: no synthetic contract test against SAP's live endpoints (would introduce test flake). The chassis' failure-per-source-is-non-fatal handling is the safety net.

#### 4.2.5 Orchestrator: `srv/lib/help-docs/index.js`

```javascript
export async function fetchAllHelpDocs({ seenSourceIds = null, limit = null } = {}) {
  const [helpRows, capRows, ui5Rows] = await Promise.allSettled([
    fetchHelpSapComCorpus({ seenSourceIds, limit }),
    fetchCapCloudSapCorpus({ seenSourceIds, limit }),
    fetchUi5SapComCorpus({ seenSourceIds, limit }),
  ]);

  // Aggregate successes; failures logged but do not abort the cycle
  // (partial catalog is better than none).
  const rows = [
    ...(helpRows.status === 'fulfilled' ? helpRows.value : []),
    ...(capRows.status === 'fulfilled' ? capRows.value : []),
    ...(ui5Rows.status === 'fulfilled' ? ui5Rows.value : []),
  ];

  // Dedupe by contentHash with source precedence.
  return dedupeByContentHash(rows);
}

const SOURCE_PRECEDENCE = Object.freeze({
  'cap-cloud-sap': 3,
  'ui5-sap-com': 2,
  'help-sap-com': 1,
});

function dedupeByContentHash(rows) {
  const byHash = new Map();
  const dropped = [];
  for (const row of rows) {
    const hash = computeContentHash(row);
    const existing = byHash.get(hash);
    if (!existing) {
      byHash.set(hash, { ...row, contentHash: hash });
      continue;
    }
    // Precedence tie-break: keep higher-precedence source.
    if (SOURCE_PRECEDENCE[row.source] > SOURCE_PRECEDENCE[existing.source]) {
      dropped.push({ dupeOf: existing.slug || existing.sourceId, chosenSource: row.source, droppedSource: existing.source });
      byHash.set(hash, { ...row, contentHash: hash });
    } else {
      dropped.push({ dupeOf: row.slug || row.sourceId, chosenSource: existing.source, droppedSource: row.source });
    }
  }
  if (dropped.length > 0) {
    log.info('help-docs.dedupe', { droppedCount: dropped.length, samples: dropped.slice(0, 5) });
  }
  return [...byHash.values()];
}
```

`computeContentHash(row)` = SHA-256 of `title + description + source + product + (section || '')`. Deterministic and stable across cycles.

Failure mode: if all three fetchers reject, `fetchAllHelpDocs` returns `[]` and the cron logs `WARN: all-fetchers-failed` — chassis-standard behavior, next cycle retries.

    if (doc.section) {
      triples.push({ s: docIri, p: IMS_SECTION, o: doc.section });
    }
    triples.push({ s: docIri, p: IMS_URL, o: doc.url });

  for (const link of links) {

## 6. Cross-source dedupe: the new-risk surface

Phase 4.7 is the first sub-phase with multiple sources feeding one entity. The dedupe logic is the biggest new correctness surface.

### 6.1 Dedupe algorithm (recap)

1. Each fetcher returns `HelpDocRow[]` with `source`, `sourceId`, `title`, `description`, `product`, `section`.
2. Orchestrator computes `contentHash = SHA-256(title + description + source + product + (section || ''))` for each row.
3. Rows are inserted into a `Map<contentHash, HelpDocRow>`.
4. Collision → keep the row whose `SOURCE_PRECEDENCE[source]` is higher. `cap-cloud-sap: 3`, `ui5-sap-com: 2`, `help-sap-com: 1`.
5. Dropped rows logged at INFO with `{ dupeOf, chosenSource, droppedSource }`.

### 6.2 Why not DB-level dedupe

Content-hash-based dedupe is a **fetch-time** filter, not a DB-side sweep. Rationale:

- Prior-cycle rows with the same hash may exist (they were inserted before this dedupe logic shipped, or before a page was mirrored). Retroactive dedupe would risk deleting a row that a concept page currently links to. The `contentHash` value is captured at write time and doesn't retroactively unify old rows.
- Fetch-time dedupe is deterministic same-input-same-output. Cross-cycle stability is preserved because both sources' `sourceId`s remain stable — if cap-cloud-sap wins in cycle N, it wins in cycle N+1 too. The dropped source's row (if it exists from a prior cycle) ages out via TTL after 540 days of continued non-refresh.

### 6.3 Failure mode: dedupe misfires

If `contentHash` collides for two rows that are NOT actually duplicates (extremely rare — the hash includes title, first-2000-char description, source, product, section), the higher-precedence source wins. This is acceptable — the worst case is a real help.sap.com row is dropped in favor of an accidental cap.cloud.sap collision, and the operator can add a `pinUntil` override on the dropped row. The chassis's `pinUntil` semantic covers the escape hatch.

## 9. Budget and MAX-or-abort gate

Steady-state weekly cron cap: **500 LLM calls/cycle**. Reasoning:

- Corpus target: 600-1200 pages.
- Weekly delta: `contentHash`-cache short-circuits unchanged pages. Expected steady-state changes: 20-100 pages/week (CAP release week could hit ~200; help.sap.com and UI5 much lower).
- 500 gives 2-5× headroom over the typical week.

**First-run gate:** MAX-or-abort. The cron function aborts with error if `SELECT COUNT(*) FROM HelpDocs = 0` unless `manualTrigger: true` is passed. Operator seeds via `scripts/seed-help-docs.cjs --commit` or `seedHelpDocs()` admin action; both paths pass `manualTrigger: true` and either MAX budget or explicit `budgetOverride: Infinity`.

## 10. Cross-cutting notes

### 10.1 LOB-locator mitigation (recap of chassis rule)

`HelpDocs.description` is `LargeString` (NCLOB). Same rule as sibling entities: **never SELECT description alongside non-LOB metadata via CDS QL on HANA.** Four read sites verified:

1. **Cron upsert path** (`fetch-help-docs-job.js`): pulls only `ID/contentHash/lastExtractedHash` from existing rows.
2. **`buildHelpDocTriples`** (`kg-projection.js`): omits description entirely (title used for `rdfs:label`, not the body).
3. **`published-concepts-query.js`**: precomputes `snippet` at link-INSERT time; payload reads `snippet` (a normal column) not `description`.
4. **Neighborhood enrichment** (`kg-neighborhood.js`): reads `slug`, `title`, `source`, `product`, `url`, `anchor` only; description omitted.

### 10.2 Predicate registration

`explains` is a new predicate. It registers in:

- `srv/lib/kg-projection.js` `PREDICATE_IRIS` map (or equivalent constant).
- `PredicateType` union in `hugo-apps/src/related-graph/types.ts` and `app/explore/src/types.ts`.
- The unit test `test/unit/srv/kg-predicate-type-lockstep.test.js` (if it exists — else added).

### 10.3 SPARQL join path (for Joule)

Joule's path-finder (Phase 2) walks the KG via SPARQL. `explains` becomes a first-class edge:

```
?doc <ims:explains> ?concept
```

The path-finder learns `explains` alongside `teaches`, `discusses`, `embodies`, `officialReferenceFor`. No path-finder code change — the SPARQL queries are edge-type-agnostic; the predicate label just appears in path descriptions. Users asking "how do CAP handlers work?" get paths like `[doc:handlers] --explains--> [concept:cap-service-handlers] --teaches<--- [tutorial:cap-getting-started]`.

### 10.4 Vue bundle budget

The concept-page section is Hugo-templated (no Vue delta). The sidebar Vue delta is a single new `v-else-if` branch (~20 LoC + ~5 LoC CSS). Well under the 150KB gzip budget cap.
