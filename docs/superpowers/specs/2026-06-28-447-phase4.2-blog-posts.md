# Phase 4.2 — Blog Posts Design

**Date:** 2026-06-28
**Issue:** [#447](https://github.com/sap-tutorials/tutorials-ims/issues/447) (Phase 4.2 sub-phase)
**Parent spec:** [`2026-06-28-447-knowledge-graph-phase4-architecture.md`](./2026-06-28-447-knowledge-graph-phase4-architecture.md)
**Sibling spec:** [`2026-06-28-447-phase4.1-learning-journeys.md`](./2026-06-28-447-phase4.1-learning-journeys.md)

## §1 Goal & scope

Phase 4.2 adds **SAP Community blog posts** as the second new graph node type under the Phase 4 chassis. Each blog post links to the concepts it discusses via a `discusses` predicate. Posts surface on concept landing pages ("Blog posts discussing this") and in the tutorial-OP sidebar's `otherResources` section.

This spec inherits every chassis decision from the architecture spec verbatim — entity shape, IRI prefix slot, TTL-based GC, merge-on-write helper, ship order — and only debates content-specific details.

### In scope

- Daily cron ingesting blog posts from SAP Community (`community.sap.com`) via the Khoros search API
- One-shot historical backfill (24 months, capped at 5000 posts) via a CLI script
- `BlogPosts` + `BlogPostConceptLinks` entities (composition cascade)
- LLM-based concept extraction adapter (`blog-post-extract.js`)
- Concept-page section "Blog posts discussing this"
- Sidebar `otherResources` widening to include `blog-post` row type
- Telemetry: `kg.blog_post.linked_from_concept_page`, `kg.blog_post.linked_from_sidebar`

### Out of scope (explicit non-goals)

- Cross-content `references` predicate (blog → tutorial, blog → journey). Sub-phase 4.6 territory.
- Author FK to `Users.ID`. Author is captured as free-form `authorLogin`/`authorName`/`authorAvatarUrl` strings.
- Per-blog landing pages (`/kg/blog-post/<slug>/`). Only concept-page + sidebar surfaces.
- Authenticated Khoros service-principal credentials. The anonymous-tier `/api/2.0/search` endpoint suffices.
- Third-party SAP blogs hosted off community.sap.com (Medium, dev.to). Arch spec leaves cross-org content out permanently.

## §2 Design decisions

| ID | Decision | Rationale |
|---|---|---|
| Q1 | **Source: Khoros `/api/2.0/search` API** | The same surface `srv/lib/khoros-client.js` already uses for author search. Paginated `messages` queries return full body, topic tags, author metadata. RSS feed is too narrow (latest ~25 posts only); MCP doesn't expose blogs. |
| Q2 | **Predicate: `discusses` only** | Single predicate keeps the link table simple. Blog posts aren't curricula (no `prerequisite` analogue), aren't admin-curated (no `authoritative` flag needed), and don't reference other content types in 4.2 (deferred to 4.6). |
| Q3 | **TTL: 540 days (chassis-locked)** | `srv/lib/external-content-ttl.js` already declares `'blog-post': 540` per architecture spec. A blog post mentioning a concept is still useful 18 months later; longer than that and the post-specifics are likely stale. |
| Q4 | **Author capture: free-form string columns** | `BlogPosts.authorLogin: String(80)` + `authorName: String(200)` + `authorAvatarUrl: String(500)`. No FK to `Users`. The community-link hover-card already does lazy author lookups via `khoros-client.searchAuthor`; replicating that hot-path is unnecessary. Defers the "posts by Tom Jung" SQL-joinable case to a future evolution — tracked informally, will get an issue when the query pattern is first requested. |
| Q5 | **Cadence: daily 04:23 UTC** | SAP Community publishes ~5–10 blog posts per day. Daily catches them while their relevance is fresh. The Khoros query filters by `post_time > $sinceIso` so steady-state ticks are cheap delta fetches. |
| Q6 | **LLM body cap: 8000 chars** | Matches Phase 4.1's tier-2 (readability) cap. A blog post's first 8K chars carries the gist; longer posts get fewer concepts extracted, which is acceptable. |
| Q7 | **Backfill: 24 months, 5000-post cap** | Khoros holds ~20K posts of history; 24 months captures the bulk of currently-relevant content. The 5000 cap is a deliberate LLM-cost budget gate. Steady state is delta-only after backfill. |
| Q8 | **Budget gates: per-day + one-shot script** | `ChatSettings.blogPostExtractBudgetPerDay` (default 50) governs the daily cron. The 5000-post backfill runs as a CLI script that bypasses the per-day gate (separate operator-initiated audit trail). Mirrors the Phase 4.1 chassis pattern. |
| Q9 | **Client module: new `khoros-blogs-client.js`** | Honest scope: Khoros isn't `sap-devs`. The chassis spec said `sap-devs-client.js` would handle 4.1, 4.2, 4.4 — that assumed all three went through MCP. Phase 4.2 doesn't, so it gets its own client. Pattern (in-process cache + on-disk cache + `_setMockTransport` + validator) mirrors `sap-devs-client.js`. **Implication for 4.4 (Videos):** Videos *do* go through the `sap-devs` MCP per arch §3.8, so 4.4 should honor the chassis client and not depart by precedent. |
| Q10 | **UI surfaces: concept-page + sidebar** | Identical to Phase 4.1 (concept page section + sidebar `otherResources` widening). No new page surfaces. |

## §3 Architecture

```text
SAP Community (Khoros)
  ├─ /api/2.0/search  ← srv/lib/khoros-blogs-client.js (NEW)
  │                      • paginated search by post_time DESC
  │                      • since-filter for delta fetches
  │                      • on-disk + in-process TTL cache (mirrors sap-devs-client pattern)
  │                      • _setMockTransport / _resetCache test hooks
  │
  └─ HANA
      ├─ BlogPosts entity                         (db/external-content.cds)
      └─ BlogPostConceptLinks (Composition)       (predicate: 'discusses')

LLM pipeline (mirrors 4.1):
  fetch listing → upsert → extract (discusses shape) → resolveConceptCandidates
                                                          (existing srv/lib/kg-merge-on-write.js)
                                                       → BlogPostConceptLinks INSERT
                                                       → UPDATE lastExtractedHash (#708 gate)

UI:
  hugo/layouts/concepts/single.html  — adds 3rd section "Blog posts discussing this"
  hugo-apps/src/related-graph/       — OtherResource.type widens to include 'blog-post'
    types.ts + RelatedGraph.vue        renders blog-post rows with "· by Author · Date"

Cron + scripts:
  srv/jobs/fetch-blog-posts-job.js   — daily 04:23 (registered in scheduler.js)
  scripts/seed-blog-posts.cjs         — one-shot 24-month backfill, bypasses daily gate
```

### Chassis lifts (unchanged from arch spec)

- IRI prefix slot: `'blog-post': 'https://developers.sap.com/kg/blog-post/'` (already reserved in arch spec)
- `SHORT_BY_TYPE` map adds `'blog-post': 'bp'` for explore-graph IRI parsing
- TTL: `external-content-ttl.js` already declares `'blog-post': 540` from Phase 4.1
- GC cron: `srv/jobs/gc-external-content-job.js` iteration set extends to include `BlogPosts` (Composition handles link-table cascade). **No `pinUntil` UI** for blog posts in 4.2 — at 2×540 = 1080 days post-`lastSeenAt`, the GC hard-deletes the row. There's no admin surface to pin an aging blog post; this is intentional (blog freshness decays naturally; pinning would require a UI investment beyond 4.2 scope). A 4.6+ admin UI revisit could add pin support uniformly across all content types.
- Merge-on-write: `srv/lib/kg-merge-on-write.js` (from #707) reused verbatim for `discusses` cover-resolution
- Crash-safety gate: `lastExtractedHash` column (from #708) — pattern carries over to `BlogPosts`

## §4 Schema (`db/external-content.cds`)

```cds
entity BlogPosts : cuid, managed {
  slug              : String(120) @assert.unique;     // derived: bp-<khorosMessageId>
  title             : String(400);                    // Khoros subject
  excerpt           : String(1000);                   // first 280 chars of body, for sidebar
  url               : String(500);                    // canonical community.sap.com URL
  khorosMessageId   : String(40);                     // Khoros numeric ID (natural key)
  postedAt          : Timestamp;                      // Khoros post_time
  // Author — free-form per Q4.
  authorLogin       : String(80);
  authorName        : String(200);
  authorAvatarUrl   : String(500);
  // Chassis columns:
  sourceId          : String(120);                    // mirrors khorosMessageId
  contentHash       : String(64);
  lastExtractedHash : String(64);                     // #708 crash-safety
  firstSeenAt       : Timestamp @cds.on.insert: $now;
  lastSeenAt        : Timestamp;
  pinUntil          : Timestamp;

  links : Composition of many BlogPostConceptLinks on links.post = $self;
}

entity BlogPostConceptLinks : cuid, managed {
  post         : Association to BlogPosts @assert.notNull;
  concept      : Association to ims.Concepts @assert.notNull;
  predicate    : String(20) default 'discusses';
  confidence   : Decimal(3, 2);
  extractedAt  : Timestamp;
  modelVersion : String(40);
}

annotate BlogPostConceptLinks with
  @assert.unique.postConcept : [post, concept];
```

### Slug derivation

`bp-${khorosMessageId}`. Globally unique (Khoros message IDs never collide), stable across title renames, namespace-separated from tutorials/journeys/concepts by the chassis IRI prefix regardless.

Observed Khoros `message_id` length: 6–8 digits in current SAP Community data (e.g. `13412493`, `14412493` from existing references in `CLAUDE.md`). `bp-<id>` therefore fits comfortably in ~12 chars; `String(120)` is generous headroom — chosen to match the `LearningJourneys.slug : String(120)` precedent rather than to accommodate any plausible message_id length.

### Why `excerpt` is a stored column

Sidebar's `otherResources` row needs a short snippet for hover-card or list-item context. Computing it on every neighborhood lookup would force `BlogPosts.body` to load — but we don't store the body (next point). So excerpt is captured at upsert time.

### Why no `body` column

Khoros body fetched fresh during the daily cron's extraction step is sufficient. Storing ~5000 × ~10KB blog bodies = ~50MB at rest with no clear consumer beyond extraction. The LLM's output (concepts + confidence) is what we persist; the body itself is ephemeral. Differs from Phase 4.1, where `LearningJourneys.description` was a fallback for the tier-3 metadata case. Khoros doesn't return empty bodies, so no fallback needed.

### Asymmetries with `LearningJourneys` (deliberate)

1. **No `description` column.** Excerpt substitutes.
2. **`khorosMessageId` is the natural key, not the slug.** Protects against silent corpus fragmentation if Khoros allows title edits (rare but possible).

### Public surface

```javascript
export async function searchBlogPosts({

  pageSize = 50,        // Khoros max per page
  pageToken = null,     // opaque pagination cursor; Khoros returns 'next_cursor'
  limit = null,         // hard cap on total results (e.g. 5000 for backfill)
} = {}) {
  // → { posts: BlogPostRow[], nextPageToken: string|null, totalReturned: number }
}

export function _setMockTransport(transport);  // test hook
export function _resetCache();                  // test hook
```

`BlogPostRow` shape (validated):

```typescript
{
  message_id: string,          // numeric in practice but string-safe
  subject: string,             // post title
  body: string,                // raw HTML
  post_time: string,           // ISO timestamp
  view_href: string,           // canonical URL
  board: { id: string },
  author: {
    login: string,
    first_name: string,
    last_name: string,
    avatar: { profile: string },
  },
}
```

### LiQL query

```sql
SELECT message_id, subject, body, post_time, view_href, board.id,
       author.login, author.first_name, author.last_name, author.avatar.profile
FROM messages
WHERE interaction_style = 'blog'
  AND post_time > '${sinceIso}'
ORDER BY post_time DESC
LIMIT ${pageSize}
```

If `sinceIso` is null, the WHERE clause drops the post_time predicate (backfill mode).

**Injection safety**: LiQL doesn't support parameterised queries, mirroring `khoros-client.js`'s search pattern. `sinceIso` is produced internally by `new Date(...).toISOString()` — never user-controlled — so the string interpolation is safe by construction. The validator at module entry guards against any caller passing a non-ISO string (throw on regex mismatch); operator-facing input via `seed-blog-posts.cjs` flags is sanitised the same way.

### Caching

- **In-process Map** keyed by `searchBlogPosts:sha256(JSON.stringify(params))`, 30-minute TTL.
- **On-disk JSON** under `.cache/khoros-blogs/<hash>.json` (gitignored). Mirrors `sap-devs-client.js`'s disk-cache discipline so dev/test re-runs are cheap.
- **Cache opt-out for backfill**: `searchBlogPosts({ cache: false })` skips both layers. The 24-month backfill spans ~100 pages; cached, that's ~100 JSON files in `.cache/khoros-blogs/` after one run. `scripts/seed-blog-posts.cjs` passes `cache: false` by default (operator-grade pagination is single-shot; caching pages just bloats disk for no replay value).

### Validator

Throws on missing/wrong-typed fields. Per the project's `feedback_silent_swallow_hides_dead_code` memory: an upstream rename or field removal must fail loudly, not silently strip rows.

## §6 Extraction adapter (`srv/lib/blog-post-extract.js`)

Mirrors `learning-journey-extract.js` with these differences:

- **System prompt:** "You are extracting concepts from an SAP Community blog post. Identify the technical concepts the post discusses. Blog posts are more focused than learning journeys — aim for 3-6 concepts."
- **LLM schema:** `{ discusses: [{slug, name, confidence}] }`. Single predicate. `name` required per the #707 merge-on-write contract.
- **Post-LLM validation:**
  - Confidence floor: 0.6 (same as 4.1's covers)
  - Cap at 6 covers (lower than 4.1's 8 because blogs are narrower)
  - Required `name` field (strip rows missing it; defends against LLM drift)
  - Slug regex: `^[a-z0-9][a-z0-9-]{0,78}[a-z0-9]$` (same as 4.1)

## §7 Cron orchestration (`srv/jobs/fetch-blog-posts-job.js`)

Schedule: `'23 4 * * *'` (daily 04:23 UTC, off-minute). Registered after the existing journey cron in `srv/jobs/scheduler.js`.

```text
1. Read ChatSettings.blogPostExtractBudgetPerDay (default 50). If <= 0, exit clean.
2. Load merge-on-write configuration:
   - mergeSimThresholdExtract from KnowledgeGraphSettings (default 0.85)
   - embeddingModel from ChatSettings (default text-embedding-3-small)
3. Load Concepts registry once: loadConceptRegistry(db).
4. Determine sinceIso:
   - sinceIso = SELECT MAX(postedAt) FROM BlogPosts
   - If empty (no rows yet): ABORT cycle with a logged warning instructing the
     operator to run scripts/seed-blog-posts.cjs first (§8 backfill). The cron
     refuses to self-bootstrap from scratch — a fresh deploy must be seeded
     deliberately, not silently populated with the last N days from cron alone.
   - This makes the daily cron's contract precise: "delta from MAX(postedAt)
     forward, refusing to operate when MAX is null."
5. Page through Khoros via searchBlogPosts({ sinceIso, pageSize: 50 }):
   for each post in page.posts:
     a. Derive slug = `bp-${post.message_id}`.
     b. Compute contentHash = sha256(subject + body + post_time).
     c. Upsert BlogPosts row (chassis pattern):
        - existing && lastExtractedHash === contentHash → skipped++; skip extraction
        - else → push to extractQueue
6. For each entry in extractQueue:
   - If extracted >= budget: break (log "budget exhausted; deferring N to next cycle").
   - Call extractConceptsFromBlogPost (body cap 8000 chars).
   - Call resolveConceptCandidates({ candidates: result.discusses, registry, embed, ... }).
   - In sequence (no explicit tx, autocommit per INSERT):
     a. INSERT pendingMints into Concepts (FK targets for the links).
     b. Warm registry with new mints.
     c. DELETE existing BlogPostConceptLinks for this post.
     d. Dedup resolved by conceptId (highest-confidence wins) — @assert.unique.postConcept.
     e. INSERT new BlogPostConceptLinks.
     f. UPDATE BlogPosts SET lastExtractedHash = contentHash (#708 crash-safety; final step).
   - summary.extracted++; merge counters from resolution.
7. Log summary.
```

### §7.1 Failure modes

Phase 4.2 bypasses the `sap-devs` MCP and goes direct to Khoros; the arch spec §3.6 MCP failure modes don't apply. Khoros-specific failure handling:

| Failure | Cron behavior | `lastSeenAt` / `lastExtractedHash` |
|---|---|---|
| Khoros 5xx mid-pagination | Abort cycle. Log `LOG.error('blog-cron: khoros 5xx at page N; aborting cycle')`. Already-fetched-and-extracted posts stay persisted. | `BlogPosts.lastSeenAt` updated only for fully-upserted rows. Posts beyond the failure page are re-fetched next cycle because their `MAX(postedAt)` hasn't advanced past them. |
| Khoros anonymous-tier rate-limit (429) | Same as 5xx — abort cycle cleanly. Log explicit "rate limited; retry next cycle". | Same as above. |
| Validator throws on a single bad row | Skip the bad row, `summary.errors++`, continue with the rest of the page. | Bad row never reaches `BlogPosts`; surfaces as `summary.errors > 0` in pipeline log. |
| LLM extract throws mid-`extractQueue` | Skip that post, `summary.errors++`, continue with the rest. | The skipped post's `lastExtractedHash` stays at its previous value — `needsExtraction` re-fires next cycle (#708 pattern). |
| Budget exhausted mid-`extractQueue` | Break loop, set `summary.budgetExhausted = true`, log "deferring N posts to next cycle". | Deferred posts' `lastExtractedHash` stays at their previous value; they re-extract next cycle. |
| Partial failure between step 6.a (Concepts INSERT) and 6.f (lastExtractedHash UPDATE) | Process dies — Concepts persist (autocommit), links may or may not exist, `lastExtractedHash` stays at its previous value. | Next cycle re-fires step 6 for this post: DELETE-then-INSERT replaces the partial link state; orphan Concepts from the prior partial run get reused by merge-on-write (or eventually GC'd by `consolidateConcepts`). Harmless. |

The unifying invariant: `lastExtractedHash` is the cron's single source of truth for "this post has been fully processed at this contentHash." Any in-progress state that doesn't reach 6.f is implicitly retryable.

### Summary shape

```javascript
{
  fetched: 0,             // posts seen from Khoros listing
  upserted: 0,            // rows touched in BlogPosts
  extracted: 0,           // LLM calls made
  skippedNoChange: 0,     // contentHash matched, no re-extract
  // #707 counters:
  mergedAtExtract: 0,
  mintedAtExtract: 0,
  skippedNoEmbed: 0,
  discussesWritten: 0,    // BlogPostConceptLinks rows INSERTed
  promptTokens: 0,
  completionTokens: 0,
  errors: 0,
  budgetExhausted: false,
}
```

## §8 Backfill script (`scripts/seed-blog-posts.cjs`)

CLI flags:

```bash
node scripts/seed-blog-posts.cjs --months=24 --limit=5000 --dry-run
node scripts/seed-blog-posts.cjs --months=24 --limit=5000 --commit
node scripts/seed-blog-posts.cjs --resume --commit
```

**Behavior:**

- Bypasses `ChatSettings.blogPostExtractBudgetPerDay` (separate operator-initiated path)
- Logs per-100-post progress to stdout
- Writes a JSON summary to `.migration-data/blog-posts-backfill-<timestamp>.json`
- Aborts cleanly on SIGINT; resumable via `--resume` (reads `MAX(postedAt) FROM BlogPosts` and continues)
- Pipeline-log entry distinguishes via `initiator` field (e.g. `manual/blog-backfill`)
- Failure modes: Khoros 5xx is retried with exponential backoff (mirrors khoros-client.js)

### Neighborhood enrichment (`srv/knowledge-graph-service.js`)

The 4.1 enrichment returned top-5 journeys by overlap. Phase 4.2 widens to UNION across journeys + blog posts:

```javascript
// Existing 4.1 logic produces journeyOverlaps from teachesConceptIds. Parallel query for blogs:
const blogOverlaps = await SELECT.from(BlogPostConceptLinks)
  .columns('post_ID', 'count(*) as overlap')
  .where({ concept_ID: { in: teachesConceptIds } })
  .groupBy('post_ID');

const blogRows = blogOverlaps.length
  ? await SELECT.from(BlogPosts)
      .columns('ID', 'slug', 'title', 'url', 'authorName', 'postedAt')
      .where({ ID: { in: blogOverlaps.map(b => b.post_ID) } })
  : [];

// Merge journeys + blogs; sort by overlap; cap top-5 TOTAL across types.
const combined = [
  ...journeyRows.map(j => ({ type: 'learning-journey', /* ... */ })),
  ...blogRows.map(b => ({
    type: 'blog-post', slug: b.slug, title: b.title, url: b.url,
    authorName: b.authorName, postedAt: b.postedAt, overlapCount: ...
  })),
].sort((a, b) => b.overlapCount - a.overlapCount).slice(0, 5);
```

**Design constraint:** sidebar shows **top-5 total** across content types, not top-5 per type. A heavily-discussed concept might surface 5 journeys and 0 blogs, or vice versa. This is correct — sidebar's job is "most-related external content," not "type diversity."

### Acceptance criteria

1. **Backfill succeeds.** `node scripts/seed-blog-posts.cjs --months=24 --limit=5000 --commit` populates `BlogPosts` with ≥ 4000 rows and `BlogPostConceptLinks` with ≥ 8000 rows.

   *Basis for the row-count expectations:* SAP Community blog publishing rate is ~5-10/day (verified via the `community.sap.com/khhcw49343/rss/Community?interaction.style=blog` feed consumed by `homepage-service.js`); 24 months ≈ 730 days × ~7/day ≈ 5100 posts available in window. The 5000 cap is a soft ceiling, so ≥ 4000 captures backfill-yielded-most-of-what's-available. Phase 4.1 extraction yielded ~3 covers/journey at LLM floor 0.6; blogs are narrower (cap 6, expected average 2-3 — see §6), so 4000 posts × 2 covers = 8000 link rows is a conservative floor. Both numbers are observable acceptance targets, not exact predictions.

2. **Daily cron is idempotent.** Two consecutive runs with no upstream changes leave row counts unchanged; `summary.skippedNoChange == fetched`.
3. **Crash-safety holds.** Test-only abort signal between `DELETE links` and `INSERT links` leaves `lastExtractedHash` at its previous value; next cycle re-extracts.
4. **Concept pages render.** A test concept's page on the DEV approuter shows a non-empty "Blog posts discussing this" section after the daily cron has run + content has been published.
5. **Sidebar shows blog rows.** Tutorial-OP sidebar displays at least one `blog-post` row when the tutorial's concepts overlap with at least one indexed post.
6. **Telemetry events fire** on click in both surfaces (`kg.blog_post.linked_from_concept_page`, `kg.blog_post.linked_from_sidebar`).
7. **Merge-on-write reuses #707.** A blog post mentioning a novel concept slug ends up in `Concepts` either as merged-or-minted; `skippedNoEmbed` counts only true embed failures.

### Backfill cost basis

5000-post backfill at gpt-4o-mini (~$0.150 / 1M input, $0.600 / 1M output as of 2026-06 — verify against the model's published price at run-time before committing). Per-post extraction: ~3K input + ~500 output tokens. Total: 5000 × (3000 × 0.00000015 + 500 × 0.0000006) ≈ 5000 × 0.00075 ≈ **$3.75 one-time**. Embedding cost is negligible (5000 × 1 call × text-embedding-3-small at $0.00002/1K tokens ≈ $0.01).

The daily cron at steady-state (50 posts/day default budget) is ~$0.04/day = ~$15/year — well under the operational noise floor.
