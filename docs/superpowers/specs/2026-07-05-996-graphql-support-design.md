# GraphQL Support for Major Services — Design

**Issue:** [sap-tutorials/tutorials-ims#996](https://github.com/sap-tutorials/tutorials-ims/issues/996)
**Status:** Design — pending user review
**Date:** 2026-07-05
**Target:** DEV first; PROD alongside AEM cutover (end of July 2026)

## Summary

Add a public, external-facing GraphQL endpoint to the tutorials platform. Read-only in v1. Auto-generated schema from four CAP services via `@cap-js/graphql`. Two mount points: an anonymous `/graphql/public` for public data, an authenticated `/graphql` (XSUAA scope `Tutorial.API`) that additionally exposes user-scoped reads. Additive-only schema evolution enforced by a CI breaking-change guard.

Mutations, subscriptions, admin/author surfaces, and query-complexity limits are explicit non-goals for v1.

## Scope & Contract

### In scope (v1)

Four services annotated with `@graphql`:

| Service | Path (OData) | Exposure |
|---|---|---|
| `HomepageService` | `/homepage` (`@requires:'any'`) | All public read entities. |
| `KnowledgeGraphService` | `/graph` | Public entities only: `Concepts`, `ConceptEdges`, `TutorialConceptLinks`. Admin projections and actions (`pathBetween`, `neighborhood`, `promoteCommunityToMission`, etc.) stay off. |
| `SearchService` | `/search` (`@requires:'any'`) | Full-text tutorial/mission/group search. |
| `DeveloperService` | `/api` (`@requires:'any'`) | Public reads. User-scoped `me`-shaped reads (progress, completions, badges) require XSUAA scope `Tutorial.API`. |

### Not in scope (v1)

- Mutations — deferred.
- Subscriptions — `@cap-js/graphql` does not support them.
- Draft-enabled entities — plugin does not support them; would leak `AdminService` internals anyway.
- Unbound / bound actions — plugin does not support them; `pathBetween`, `neighborhood`, `promoteCommunityToMission`, etc. remain OData-only.
- HANA BLOB streams (`Tutorials.contentHtml`) — served over the existing `/content/*` path, not through GraphQL.
- `AdminService`, `AuthorService`, `ExportsService`, `AnalyticsService`, `ChatService`, `DisplayService`, `EventStreamService`, `ScannerService`, `ConsolidationService`, `CronService`.

### Schema shape

Auto-generated by `@cap-js/graphql`. Service names become schema namespaces:

```graphql
type Query {
  HomepageService: HomepageService_Query
  KnowledgeGraphService: KnowledgeGraphService_Query
  SearchService: SearchService_Query
  DeveloperService: DeveloperService_Query
}
```

Internal CDS entity and field names become the public contract from day one — this is an accepted trade-off for zero-resolver-code v1.

### Versioning

Single evolving endpoint. Additive-only semantics.

- New fields, new entities, new optional args → free to ship.
- Renames → keep the old element with `@deprecated: { reason, successor }`, add the new element alongside; both coexist for ≥ one release; release-note announcement.
- Deletions, type narrowings, adding a required arg → mark the outgoing element / arg / type-position `@deprecated`, keep it for ≥ one release, then remove; release-note announcement.
- Enforced by a CI job that diffs the emitted `graphql/schema.graphql` against the frozen `graphql/.last-release.graphql` and fails on non-additive changes without a corresponding `@deprecated`.

## Auth Model

Two mount points, single plugin registration filtered per endpoint:

| Endpoint | AppRouter auth | XSUAA scope | Visible services |
|---|---|---|---|
| `/graphql/public` | `authenticationType: none` | — | `HomepageService`, `KnowledgeGraphService` (public entities), `SearchService` |
| `/graphql` | `authenticationType: xsuaa` | `Tutorial.API` for `me.*` fields | All four services; `DeveloperService` user-scoped reads gated at the field level |

External developers obtain a bearer token via one of the standard XSUAA OAuth2 flows:

- **Authorization code + PKCE** — for interactive integrations (e.g. a partner web app).
- **Client credentials** — for backend-to-backend integrations. Requires a service key on the tutorials `xsuaa` instance.

Both flows are documented in the public docs page (see below).

New XSUAA scope `Tutorial.API` and role template `Tutorial API Consumer` added to `xs-security.json` **and** `.deploy/xs-security.json` (dual-file drift is caught by `test/unit/xs-security-authorities.test.js`).

### Open validation item (plan Task 1)

`@cap-js/graphql` may not support per-endpoint service filtering directly. The plan's first task validates this against the plugin's actual API. Fallback: collapse to a single authenticated `/graphql`, accept that external `curl` demos need a token even for public data, update the docs page accordingly. This fallback is shippable but degrades DX; validating upfront avoids a mid-plan pivot.

### AppRouter routes (new)

Added to `approuter/xs-app.json`, **placed before** the existing `^/graph/(.*)$` route to prevent the KG route from swallowing `/graph…l` requests:

```json
{ "source": "^/graphql/public(\\?.*)?$", "target": "/graphql/public",
  "destination": "srv-api", "authenticationType": "none" },
{ "source": "^/graphql(\\?.*)?$", "target": "/graphql",
  "destination": "srv-api", "authenticationType": "xsuaa" }
```

### Runtime dependencies

- `@cap-js/graphql` (production).
- No `graphql-depth-limit` / `graphql-query-complexity` in v1 (see Safety Limits).

### Data flow — public read

```
curl /graphql/public
  → approuter (auth: none)
  → srv-api /graphql/public
  → @cap-js/graphql resolver (filtered to 3 public services)
  → cds.connect.to('HomepageService').run(SELECT …)
  → HANA
  → JSON response
```

### Data flow — authenticated read

```
curl -H "Authorization: Bearer …" /graphql
  → approuter validates XSUAA token, forwards
  → srv-api /graphql
  → @cap-js/graphql resolver, req.user populated
  → DeveloperService, @requires: 'Tutorial.API' on me.*
  → CDS enforces field-level scope; 403 if scope missing
  → JSON response
```

### Docs page

Hugo page at `/api-docs/graphql/`, static content, no Vue island. Sections:

1. Quickstart — three example queries (public homepage shelves; `search(q: "cap")`; authenticated `me.completions`).
2. Auth walkthrough — both OAuth flows with `curl` and Node examples.
3. Schema — link to downloadable `graphql/schema.graphql`, link to GraphiQL.
4. Versioning policy — brief statement of the additive-only contract.

Added as one entry to the existing docs shelf; no new navigation infrastructure.

### Build & deploy

`npm run build:all` gains one step: `scripts/emit-graphql-sdl.ts` runs after `cds build --production` and writes `graphql/schema.graphql`. The SDL is a build artifact for CI and the Hugo docs page — not required at runtime by the CAP server.

`cds build --production` is required (not `cds compile`) — see the CAP-CDS gotchas doc.

## Error Handling, Testing, Observability

### Error handling

`@cap-js/graphql` translates CDS errors into GraphQL `errors[]` per the spec:

| Cause | `errors[].extensions.code` |
|---|---|
| Missing / invalid token | `UNAUTHENTICATED` |
| Missing `Tutorial.API` scope | `FORBIDDEN` |
| Malformed query / invalid arg | `BAD_USER_INPUT` |
| CAP handler throws | `INTERNAL_SERVER_ERROR` |

`NODE_ENV=production` strips stack traces from `errors[]`. Verified in the smoke test.

Introspection is **on** in all environments — the schema is published anyway, and external devs need it for tooling.

### Testing

Four layers, mirroring the existing `test/{unit,hybrid,smoke}` split.

1. **Unit — schema shape** (`test/unit/graphql-schema-shape.test.js`)
   - Boot CAP, load the plugin, compile the schema, snapshot to string.
   - Assert `Query` namespaces = `{HomepageService, KnowledgeGraphService, SearchService, DeveloperService}` exactly.
   - Assert no draft-marker types leak: regex `!/HasActiveEntity|SiblingEntity|IsActiveEntity/` over the SDL.
   - Deny-list assertion: `KnowledgeGraphService` admin entities (`ConceptClusters`, `KgCommunities`, `KgCommunityMembers`, etc.) are absent.

2. **Unit — breaking-change guard** (`test/unit/graphql-breaking-change.test.js`)
   - Runs `check-graphql-breaking.ts` against `graphql/.last-release.graphql`.
   - Fails on: deletions, type narrowings, required-arg additions.
   - Passes on: any additive change; any change accompanied by `@deprecated` on the outgoing element.
   - Runs in CI on every PR.

3. **Hybrid — endpoint** (`test/hybrid/graphql-endpoint.test.js`, `--project hybrid`)
   - `/graphql/public` with no token → 200 for `HomepageService.HomepageShelves`, `errors[].code: UNAUTHENTICATED` for `DeveloperService.me`.
   - `/graphql` with `Tutorial.API`-scoped token → 200 for `me.completions`.
   - `/graphql` with a token lacking `Tutorial.API` → `errors[].code: FORBIDDEN`.
   - Reminder: always pass `--project hybrid` when running the file directly.

4. **Smoke** (`test/smoke/graphql-smoke.test.js`)
   - Three curl-style queries against `SMOKE_APPROUTER_URL` post-deploy.

### Observability

- `@cap-js/telemetry` already instruments CAP handlers; GraphQL resolvers dispatch through the same pipeline, so per-service spans are free.
- No custom metrics module in v1. If usage warrants it, a follow-up adds `graphql_operation_duration_ms{operation, service}` and `graphql_operation_errors_total{code}`.
- Log level: `@cap-js/graphql` logs parsed operation names at `info`, not full query strings. Documented in the reference note.

## Safety Limits (v1)

Explicit v1 posture: **bare minimum** (per user decision at brainstorming Q7).

- Rate limiting: per-IP at AppRouter (existing behavior; nothing GraphQL-specific).
- Depth limit: **none**.
- Query cost / complexity limit: **none**.
- Introspection: **on** in all environments.
- Persisted queries: **not required**.

The reference doc flags "revisit if abuse observed." Adding `graphql-depth-limit` and `graphql-query-complexity` is a config-only change later.

## Rollout Plan

1. **DEV deploy** with both endpoints live. `Tutorial.API` scope granted only to a small internal test role collection. No public announcement.
2. **Internal validation** — hybrid tests + manual GraphiQL exploration. Confirm the two-endpoint filter works. If it doesn't, execute the Section 2 fallback (single authenticated `/graphql`, update docs page).
3. **QA channel** — same routes added to the `srv-qa` approuter for author-side manual testing.
4. **Docs page published** to `/api-docs/graphql/` on the DEV Hugo build; link stays unlisted until sign-off.
5. **PROD cutover** — enable in the same MTA deploy as the AEM decommission (end of July 2026). Announce via standard developers.sap.com channels.

## Risks & Mitigations

| Risk | Mitigation |
|---|---|
| `@cap-js/graphql` doesn't support per-endpoint service filtering | Plan Task 1 validates this against the plugin API. Fallback: single authenticated `/graphql`. |
| Auto-generated schema leaks internal CDS names → future rename becomes breaking API change | Accepted trade-off. Breaking-change CI guard forces us to be explicit. |
| Draft-enabled entities auto-included by the plugin → surface admin data | Schema-shape unit test asserts no `HasActiveEntity`/`SiblingEntity` types. |
| No query complexity limits → single-endpoint DoS via nested queries | Accepted for v1. Reference doc flags "revisit if abuse observed." |
| Introspection on in prod → scrapers pull the schema | Accepted (public API; schema is published anyway). |
| Admin actions (`pathBetween`, `promoteCommunityToMission`) look exposable via `@graphql` but plugin skips them silently | Documented in reference note. Schema-shape test asserts they don't appear. |
| CAP 10's `service_level_restrictions` (now `true`) — `@requires` enforced on local resolver-to-service calls | This is desired. Hybrid test explicitly exercises it. |
| New `Tutorial.API` scope → dual-file `xs-security.json` drift | Existing `test/unit/xs-security-authorities.test.js` catches this. |
| Rate limiting is per-IP; one misbehaving key can DoS its origin | Out of scope for v1; noted for follow-up. |
| Introducing `@graphql` on a draft-enabled service later would silently opt it in | Schema-shape test acts as a regression guard on every PR. |

## Deferred (explicit non-goals for #996)

- Mutations (`enrollInMission`, `markStepComplete`, etc.) — requires a design pass on write auth and idempotency.
- Subscriptions — plugin doesn't support them; would need a custom `graphql-ws` adapter on top of the existing Socket.IO infra.
- Persisted queries + query complexity limits — revisit if v1 traffic warrants.
- Custom resolvers spanning multiple services (`tutorial.mission.group` in a single query) — the auto-generated per-service schema keeps services siloed. A curated top-level `Query` is a separate design.
- Rate limiting per API key rather than per IP.
- GraphQL over WebSocket / SSE for real-time event streams — the existing `/ws/*` Socket.IO surface stays canonical.
