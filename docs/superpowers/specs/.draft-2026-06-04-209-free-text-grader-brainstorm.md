## Surface map (facts, not decisions)

### Current state of `[VALIDATE_N]` text-question grading

`hugo/assets/js/tutorial.ts:430-433` — the existing grading code:

```typescript
const input = form.querySelector(`input[name="${name}"]`)
if (!input || input.value.trim().toLowerCase() !== q.correctAnswer.toLowerCase()) allCorrect = false
```

Plain case-insensitive string equality. No partial credit, no regex evaluation, no AI.

### Pre-existing bug worth flagging to Tom

The parser at `scripts/parsers/rules.ts:52` treats ANY non-`{single,multiple}-choice` rule type as `'text'`. Real authored `rules.vr` files contain rule types like `regex`, `regex-begins-with`, `exact-match`. The runtime treats all of them identically with case-insensitive equality — meaning **`regex`-typed answers have never actually been evaluated as regex**. A learner who answers correctly per the regex pattern but doesn't match the literal pattern string fails. This is a quality issue that's been latent since the rules.vr loader was written.

This makes the AI grader a *fix*, not just an upgrade: it would handle "is this answer correct in spirit" regardless of how the author marked the rule type.

### Reusable from PR #205

Almost all the infrastructure carries over:

- **`srv/lib/code-check-tool.js`** `dispatchCheckCode(input, deps)` shape — directly mirrorable as `dispatchValidateAnswer(input, deps)`.
- **`srv/lib/code-check-prompt.js`** — `buildSystemPrompt`, `buildUserMessage`, `CHECK_CODE_OUTPUT_SCHEMA`, `redactReferenceLeaks`, `PROMPT_VERSION`. Same export shape; new prompt content for free-text grading.
- **`srv/lib/code-check-llm.js`** `defaultCallModel({ system, user, schema })` — reusable as-is. The forced-tool-call pattern is the same.
- **`srv/lib/code-check-handler.js`** rate-limit shape (30/hour per user + 5/5min per `(user, slug, step)`, in-memory `Map`, `Retry-After` header) — directly applicable.
- **`srv/lib/anonymization-cascade.js`** default `'null-personal'` cascade — automatic for any new `@PersonalData`-annotated table.

### Reusable from PR #221

- The `@PersonalData` annotation default cascade (`null-personal`) means the new submissions table participates in user anonymization with zero JS — just annotate.

### Net new design surface

1. **Opt-in mechanism** — per-question, per-rule, or all-text-questions-when-flag-on?
2. **Existing widget integration** — extend `tutorial.ts:421-447` to call a new endpoint, or build a separate Vue island?
3. **Prompt content** — different from code-check (grading a sentence-answer against a correct answer, not grading code against a goal).
4. **Output schema** — what verdict shape? Same `pass/partial/fail` enum?

## Proposed design (my recommendations)

### Architecture

```
hugo/assets/js/tutorial.ts (existing)               srv/server.js
  initValidation() (existing)                          POST /api/validate-answer (NEW)
  renderQuiz() (existing)                                ↓
  handleQuizSubmit() ───────────────────────────► validateAnswerHandler
    if any text question has aiGrading:                ↓
      POST {tutorialSlug, step, answers}        srv/lib/validate-answer-tool.js
    else:                                              ↓
      grade locally (existing exact-match)        dispatchValidateAnswer
                                                       ↓
                                                    forced-tool-call LLM
                                                       ↓
                                                    persist ValidateAnswerSubmissions
                                                       ↓
                                                    return {verdict, summary, ...}
```

The widget keeps its current local exact-match path for backward compat. When AI grading is enabled per-step, the submit handler hits a new endpoint instead.

### CDS schema additions

```cds
entity ValidateAnswerSubmissions : managed {
  key ID            : UUID;
  user              : Association to Users;
  tutorialSlug      : String(200) @mandatory;
  stepNumber        : Integer @mandatory;
  questionId        : String(40);                // 'validate-{stepNum}' or future per-question id
  questionText      : LargeString;               // captured for telemetry context
  correctAnswer     : LargeString;               // author's expected answer (for eval)
  submittedAnswer   : LargeString @mandatory;    // learner's answer
  verdict           : String(10);                // 'pass'|'partial'|'fail'|'error'
  summary           : LargeString;               // AI feedback
  modelName         : String(80);
  promptTokens      : Integer;
  completionTokens  : Integer;
  latencyMs         : Integer;
  errorReason       : String(200);
}

extend ChatSettings with {
  validateAnswerEnabled : Boolean default false;
}
```

`@PersonalData` annotation in `db/audit-logging.cds`:

```cds
annotate ims.ValidateAnswerSubmissions with @PersonalData: {
  EntitySemantics: 'Other'
} {
  user             @PersonalData.FieldSemantics: 'DataSubjectID';
  submittedAnswer  @PersonalData.IsPotentiallyPersonal;
};
```

Default cascade (`null-personal`) handles user anonymization automatically (PR #221).

### Prompt design (proposed)

The prompt teaches the model to grade "is this answer correct in spirit" and is more permissive than exact match.

System prompt (paraphrased):

```
You are a patient tutorial grader evaluating a learner's answer to a text
question. You receive the question, the author's expected answer, and the
learner's answer. Grade based on whether the learner has demonstrated
understanding of the concept the question targets — not whether their
answer is verbatim equal to the author's expected answer.

Verdict scale:
- "pass": the learner's answer is essentially correct. Synonyms, paraphrases,
  and minor wording differences are FINE if they convey the same idea.
- "partial": the learner has the right concept but is missing key detail
  the author explicitly required.
- "fail": the answer addresses a different concept or is wrong.

Output JSON: { verdict, summary, hint? }. Summary is one sentence stating
the grade in plain language. Hint is optional one-sentence guidance toward
the correct answer (for partial only — empty on pass/fail).
```

Output schema:

```js
{
  type: 'object', additionalProperties: false,
  required: ['verdict', 'summary'],
  properties: {
    verdict: { type: 'string', enum: ['pass', 'partial', 'fail'] },
    summary: { type: 'string', maxLength: 300 },
    hint:    { type: 'string', maxLength: 250 }
  }
}
```

Smaller schema than code-check because the input is smaller (a sentence, not code) and the output is simpler (no `correctAspects`/`suggestions` arrays — just one summary + optional hint).

### Reference-leak guard

Reuse `redactReferenceLeaks(verdict, correctAnswer)` shape from `srv/lib/code-check-prompt.js`. The 30-char sliding-window check would protect against the model echoing the correct answer in `summary` or `hint`. For short answers (`< 30 chars`, which is the common case for crossword-style questions), the guard is a no-op — that's fine; in those cases the learner already knows from `verdict: 'pass'` what the answer was anyway.

### Express endpoint

`POST /api/validate-answer`:

```ts
{ tutorialSlug, stepNumber, questionId, submittedAnswer, language? }
→ 200 { verdict, summary, hint? }
→ 401 (anonymous)
→ 400 invalid_body | answer_too_long
→ 429 rate_limited
→ 503 disabled
→ 500 internal
```

Same rate-limit shape as code-check (30/hour per user + 5/5min per `(user, slug, step)`). Body cap 5KB (text answers are small).

### Existing widget integration (tutorial.ts)

Extend `handleQuizSubmit()` in `tutorial.ts:421-447`:

## Open questions for Tom

These are decisions I cannot make on your behalf because they affect product semantics, not implementation mechanics.

### Q1 — Opt-in mechanism for AI grading per question

Three options, each viable:

**A. Author opts in per-question via a new `###Grading` directive in `rules.vr`:**
```
[VALIDATE_3]
###Rule
exact-match
###Grading
ai-judged
###Question
What is the difference between cds.connect.to and cds.requires?
###Match
The first connects to a service at runtime; the second declares a dependency.
```

Pros: per-question control. Authors who only want AI grading for hard-to-pin-down questions get it. Backward compat: absent `###Grading` defaults to existing exact-match.

Cons: extra annotation surface for authors to learn.

**B. Per-rule-type: `regex` and `regex-begins-with` rules become AI-graded automatically when `validateAnswerEnabled: true`.**

Pros: zero new annotation. Authors who already used `regex` (and weren't actually getting regex evaluation — pre-existing bug) get a meaningful upgrade.

Cons: silent behavior change for existing rules; some authors may have intended `regex` literally and the AI would behave differently.

**C. All-or-nothing: when flag is on, all text questions go through AI grader.**

Pros: simplest mental model.

Cons: coarsest control; some authors want pure exact-match for crossword-style "type the answer" questions and would resent AI getting in the way.

**My recommendation:** A — per-question opt-in. Matches the code-check spike's per-step `[CODECHECK_N]` opt-in pattern and gives authors the most control. The annotation is one line.

### Q2 — Per-rule-type fix or AI-grader-only?

The pre-existing `regex`-treated-as-string-equality bug is real. Two ways to address it:

**A. Fix it implicitly via Q1A:** authors with `regex` rules opt those into AI grading; the rule-type annotation becomes meaningful only as a hint to the AI.

**B. Fix it explicitly:** add proper regex matching to the local widget for `regex`/`regex-begins-with` rule types, AND ALSO offer the AI grader as a separate opt-in. Two paths coexist.

**My recommendation:** A. The local widget is JS, the rules are RUNTIME, regex evaluation is a non-trivial security surface (catastrophic-backtracking DoS) and it has been broken for an unknown amount of time without anyone noticing. The right fix is to declare `regex` rule type effectively deprecated and route via AI grader. But this is a real authoring contract change and Tom should weigh in.

### Q3 — Capture `correctAnswer` in `ValidateAnswerSubmissions` for telemetry?

The schema I proposed includes `correctAnswer` (the author's expected answer) so we can analyze grader quality offline. But:

- It increases the table's privacy surface (the author wrote it, but it's now in the submissions table forever).
- It's redundant with the rules.vr file in source control.

**My recommendation:** include it. The AI code-check spike's `CodeCheckSubmissions` table doesn't capture the goal text (just slug+step) and that has made offline grading-quality eval clunkier. This avoids the same trap. But Tom's call.

### Q4 — Hybrid `@PersonalData` cascade verification

Same situation as PR #221: the new submissions table is `@PersonalData`-annotated and the cascade should work via the default `null-personal` action. PR #221's hybrid test 4 is the model — should this PR add a similar hybrid test for `ValidateAnswerSubmissions`?

**My recommendation:** yes, by precedent. Follow the same `__TEST__cc-209-`-prefix conventions.

### Q5 — Frontend integration approach

The existing `tutorial.ts:421-447` is plain TS in `hugo/assets/js/`. Two options:

**A. Extend the existing tutorial.ts in place.**

Pros: minimal disruption. The widget is already loaded on every tutorial page; adding a network call is a small change.

Cons: more network handling code in tutorial.ts (it grows ~50 lines for the new path).

**B. Build a new Vue island under `hugo-apps/src/validate-answer/`** that takes over the validation mount.

Pros: cleaner separation, matches the U1-U18 modernisation pattern.

Cons: Mostly duplicates existing `initValidation`/`renderQuiz` work. Reasonable as part of a larger #212 re-scope (Option B from the #212 issue comment) but not standalone for this ticket.

**My recommendation:** A. Issue #212's re-scoping is a separate question. For #209, the smallest cohesive change is extending tutorial.ts.

### Q6 — `'partial'` verdict UI

The proposed schema has three verdicts. The existing widget shows binary "Correct!" / "Not quite. Try again!" feedback. For `'partial'`, what UI?

**My recommendation:** add a third state: "Close — let me give you a hint." Renders the AI-supplied hint below. Tom — does this fit the existing learner UX direction?
