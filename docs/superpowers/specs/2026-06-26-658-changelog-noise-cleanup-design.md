# Changelog Noise Cleanup — Design

**Issue:** [#658 Change History — too much being recorded](https://github.com/sap-tutorials/tutorials-ims/issues/658)
**Date:** 2026-06-26
**Status:** Approved (Tom 2026-06-26)

## Problem

The admin Change History tile (`/admin-ui/#changelog-display`) is flooded with two
classes of useless entries:

1. **No-delta "Create" rows on @odata.singleton tiles.** Every fresh subaccount,
   and any time one of the singleton-backed Settings tables is emptied, the
   admin-UI tile produces a `Create` row in `sap.changelog.Changes` the *first
   time anyone opens the tile* — even when no edit takes place. The row carries
   no `valueChangedFrom`/`valueChangedTo` deltas, so it renders as a phantom
   entry in the UI.
2. **Constant churn on Concepts / ConceptEdges.** The AI extract-concepts cron
   (`srv/jobs/extract-concepts-job.js`) deletes-then-reinserts `ConceptEdges`
   rows for every tutorial on every run, and UPDATEs `Concepts.lastSeenAt +
   extractionCount` for every concept touched. The @cap-js/change-tracking
   AFTER triggers fire on each statement and write changelog rows, even when
   no admin-curated field changed.

The combined effect: an admin opening the Change History tile sees pages of
auto-generated entries before reaching any human edit. The audit signal is
buried.

## Root causes

### 1. Phantom singleton "Create" entries

[srv/admin-service.js](../../../srv/admin-service.js) lines 151–289 contain
seven `before('READ', ...)` handlers — one each for `ChatSettings`,
`KnowledgeGraphSettings`, `UiEventsSettings`, `TenantSettings`,
`DisplaySettings`, `SearchSettings`, `NavigatorSettings`. Each handler
idempotently INSERTs a default row when the backing table is empty so the
OData v4 singleton PATCH semantics don't 404 on a fresh subaccount cutover.

All seven entities carry `@changelog` in
[db/change-tracking.cds](../../../db/change-tracking.cds). The HANA AFTER
INSERT trigger generated by @cap-js/change-tracking fires on the lazy INSERT
and writes a `sap.changelog.Changes` row attributed to whoever did the first
READ. That row has empty deltas (it's a synthetic init, not a real edit), so
the UI renders it as a no-delta phantom.

The earlier `cac491d2` commit (yesterday) added the four newest singleton
auto-init handlers (Tenant/Display/Search/Navigator) and inadvertently
amplified the existing issue by widening the entity set.

### 2. KG / AI cron-driven churn

[srv/jobs/extract-concepts-job.js:436–456](../../../srv/jobs/extract-concepts-job.js)
deletes-then-reinserts `ConceptEdges` rows for every `requires` prerequisite
on every cron tick:

```js
await tx.run(
  DELETE.from(ConceptEdges).where({ source_ID, target_ID, predicate: 'requires' }),
);
await tx.run(
  INSERT.into(ConceptEdges).entries({ /* … */ }),
);
```

With `@changelog : ['status']` on `ConceptEdges` (see
[db/change-tracking.cds:26](../../../db/change-tracking.cds#L26)) the delete +
create trigger pair fires every run, regardless of whether the edge content
changed. With ~1400 tutorials and several prerequisite edges per tutorial,
this generates thousands of changelog rows per cron tick.

Same shape on `Concepts.lastSeenAt + extractionCount` UPDATEs (line 462). The
columns aren't in the tracked list, but the AFTER UPDATE trigger still fires
and evaluates each tracked column for delta — producing empty-attribute
"Update" rows in the changelog table.

## Decision

**Drop `@changelog` from the nine offending entities.** Configuration
singletons and machine-generated knowledge-graph tables are not audit material.
Real admin-managed entities (Advocates, Secrets, AnalyticsSavedQuery, the
legacy Events/Missions/Groups/Accomplishments/Prizes carrying `@changelog`
elsewhere) keep their annotations.

Plus a **one-shot historical purge** to clean the noise already accumulated in
`sap.changelog.Changes`, gated by a `JobLocks` sentinel so it runs exactly
once across CF instances and restarts. Plus a **`purgeNoiseChangeLog`
admin action** so support can re-run the purge ad-hoc.

## Changes

### A. Annotation cleanup

Edit [db/change-tracking.cds](../../../db/change-tracking.cds) — remove
`@changelog` from:

- `ims.ChatSettings`
- `ims.KnowledgeGraphSettings`
- `ims.UiEventsSettings`
- `ims.TenantSettings`
- `ims.SearchSettings`
- `ims.NavigatorSettings`
- `ims.DisplaySettings`
- `ims.Concepts`
- `ims.ConceptEdges`

Replace the deleted annotations with a comment block explaining the rationale
("configuration singletons + AI-generated tables are not audit material; see
2026-06-26-658-changelog-noise-cleanup-design.md").

Keep `@changelog` on `Advocates`, `AdvocateTopics`, `AdvocateLinks`, and
`Secrets` — those carry human-edited content that we genuinely want history
on. `AnalyticsSavedQuery` uses the separate `@cds.changelog : true` shape and
is unaffected.

### B. One-shot historical purge

New helper: [srv/lib/purge-stale-changelog.js](../../../srv/lib/purge-stale-changelog.js)
(new file) exporting:

```js
export async function purgeStaleChangelog({ entities, db } = {}) {
  // DELETE FROM sap.changelog.Changes WHERE entity IN (…)
  // Returns { deleted: <number>, alreadyRan?: true }.
  // alreadyRan is set only when called via the auto-purge wrapper and the
  // JobLocks sentinel already exists.
}

export const NOISE_ENTITIES = [
  'com.sap.developers.ims.ChatSettings',
  'com.sap.developers.ims.KnowledgeGraphSettings',
  'com.sap.developers.ims.UiEventsSettings',
  'com.sap.developers.ims.TenantSettings',
  'com.sap.developers.ims.DisplaySettings',
  'com.sap.developers.ims.SearchSettings',
  'com.sap.developers.ims.NavigatorSettings',
  'com.sap.developers.ims.Concepts',
  'com.sap.developers.ims.ConceptEdges',
];
```

Wired into [srv/server.js](../../../srv/server.js) inside the existing
`cds.on('served', …)` handler, gated by a `JobLocks` sentinel row
(`name='changelog-noise-purge-v1'`) acquired via the existing
[srv/jobs/job-lock.js](../../../srv/jobs/job-lock.js) helper
(`runWithLock` / `tryAcquireLock` — planner picks the right primitive).
First server to acquire the lock runs the purge; everyone else
short-circuits. Re-running the deploy is a no-op because the lock row
already exists.

The version suffix (`-v1`) lets us bump to `-v2` later if a new round of
purge is needed without writing one-off SQL.

### C. Admin action

Add to [srv/admin-service.cds](../../../srv/admin-service.cds):

```cds
// Bulk-purge sap.changelog.Changes rows for entities whose tracking was
// retroactively dropped (configuration singletons + AI-generated KG tables).
// Pass an empty array to use the default NOISE_ENTITIES list. Idempotent.
action purgeNoiseChangeLog(entities : array of String) returns {
  deleted : Integer;
};
```

Handler in [srv/admin-service.js](../../../srv/admin-service.js): calls the
same `purgeStaleChangelog` helper, defaulting to `NOISE_ENTITIES` when the
incoming array is empty / null.

Surface in [`app/admin/operations/`](../../../app/admin/operations/) as a
button next to the existing `clearChangeLog` action so support can re-run
the purge from the admin UI.

### D. Tests

**`test/hybrid/changelog-noise.test.js`** (new — requires `cds bind` to DEV
HANA):

1. *Triggers dropped on un-tracked singletons.* After deploy, query HANA
   `SYS.TRIGGERS WHERE SUBJECT_TABLE_NAME` for the un-tracked entities and
   assert zero AFTER triggers remain. Then force-empty `TenantSettings`
   (via the write-safety-guarded `__TEST__` test prefix pattern), trigger
   a singleton READ via the auto-init handler, and assert
   `sap.changelog.Changes WHERE entity LIKE '%TenantSettings'` count is
   still zero. (The trigger check is the load-bearing assertion; the
   count check guards against a future regression that re-adds
   `@changelog`.)
2. *Auto-purge fires once.* Seed two noise rows for `Concepts` directly into
   `sap.changelog.Changes`, then call the auto-purge helper. Assert both
   rows gone AND a `Secrets` row inserted for control is untouched.
3. *Auto-purge sentinel.* Call the helper twice; assert second call returns
   `{ deleted: 0, alreadyRan: true }`.

**`srv/__tests__/admin-service-purge-noise.test.js`** (new unit):

1. Pass `entities: ['…TenantSettings']` → only that entity's rows deleted.
2. Pass `entities: []` → all nine NOISE_ENTITIES entries deleted.

## What does NOT change

- The lazy `before('READ')` singleton auto-init handlers. They still solve the
  underlying 404-on-fresh-subaccount problem. With `@changelog` gone, the
  INSERT no longer trips a trigger.
- The 90-day retention cron in
  [srv/jobs/cleanup.js](../../../srv/jobs/cleanup.js). Still useful for
  natural decay of legitimate edit history on the entities we *keep*
  tracking.
- The existing `clearChangeLog` admin action. The new `purgeNoiseChangeLog`
  is an entity-list-driven sibling, not a replacement.

## Rollout

1. PR ships the schema change + helper + action + tests.
2. On deploy, `cds build --production` regenerates `db/last-dev/csn.json`
   without `@changelog` on the nine entities. The @cap-js/change-tracking
   plugin's `addMigrationTable.js` reconciles trigger state and emits
   `DROP TRIGGER` statements as part of the HDI deploy — verified during
   implementation; if the plugin doesn't auto-drop, an explicit
   `db/migrations/drop-changelog-triggers.hdbprocedure` is added.
3. `cds.on('served', …)` fires the one-shot purge on first boot of any CF
   instance; remaining instances no-op via the `JobLocks` sentinel.
4. Going forward, edits to any of the nine entities are normal writes with
   no changelog side effect.

## Risk

- **Plugin trigger DROP semantics.** Removing `@changelog` from an existing
  entity needs to produce a `DROP TRIGGER` in the HDI migration. The
  @cap-js/change-tracking plugin reads the current model and reconciles
  trigger state; verified during implementation. If the plugin leaves
  orphan triggers, an explicit drop migration is added.
- **Audit expectation.** None of the nine entities carry `@PersonalData` and
  none represent user-attributable data — they're feature flags / AI output.
  Dropping `@changelog` does not affect GDPR compliance posture. Called out
  in the docs update.
- **AnalyticsSavedQuery uses `@cds.changelog : true` (different shape).**
  Unaffected by this change. Its noise profile is also healthy — saved
  queries are admin-curated, edit history is genuinely useful.
- **Plugin version.** `@cap-js/change-tracking@2.0.0-beta.11` — beta release.
  Behavior on annotation removal should be verified against the plugin
  source; the relevant logic lives in `lib/hana/migrationTable.js` and
  `lib/addMigrationTable.js`.
