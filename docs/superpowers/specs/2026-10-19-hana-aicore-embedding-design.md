# HANA-Native AI Core Embeddings — DEV Setup & Proof (design)

**Issue:** [#2810](https://github.com/sap-tutorials/tutorials-ims/issues/2810)
**Date:** 2026-10-19
**Status:** design — no SQL run against HANA yet
**Scope of this unit:** basic setup only. Connect the existing AI Core
instance to the DEV HANA container and prove `VECTOR_EMBEDDING` works from
the DB layer. **No application rewrite.** Moving existing Node/CAP
embeddings into the DB is explicitly a later unit.

## Intent & why

Today every embedding this platform produces is computed at the Node/CAP
layer via `@cap-js/ai` / the AI SDK (`@sap-ai-sdk/orchestration`) calling
AI Core, then written to HANA. HANA Cloud now exposes `VECTOR_EMBEDDING`
(and a wider AI function family) that can call AI Core **from inside the
database**, removing a network round-trip and the application-side
pipeline for keeping embeddings in sync with their source text.

Before committing to any rewrite, we want a de-risking proof: reuse the
**existing** AI Core service instance + a dedicated x509 service key, wire
it into the DEV HANA container as a remote source, and confirm an
embedding can be generated by SQL. Prove it on DEV; repeat on PROD only
after.

## Goals

- Reuse the existing `tutorials-aicore` instance via the dedicated
  `hana-ai-core` (x509) service key — no new AI Core instance.
- Create the PSE + remote source **inside the `tutorials-hana` HDI
  container** (shippable shape CAP can later consume), not as a throwaway
  admin-level object.
- Extend the container user's privileges **declaratively** through the
  existing `db/src/_grants.hdbgrants` mechanism — no manual one-off
  DBADMIN grant.
- Produce a committed operations runbook so the PROD repeat is mechanical.
- Confirm two tiers of embedding work: HANA built-in NLP, and AI Core via
  the remote source.

## Non-goals / anti-goals

- **Not** rewriting any existing embedding feature (freshness corpus,
  semantic search, KG, RPT ValueList) to use DB-side embeddings. Later.
- **Not** touching PROD in this unit.
- **Anti-goal:** creating the remote source as a bare instance-level
  admin object that CAP can't reach — that would "work" in a test and
  still require a full redo to ship.
- **Anti-goal:** hand-running `GRANT` as DBADMIN outside the HDI deploy —
  it drifts from the repo and is lost on next container rebuild.

## How it gets built (the decided parts)

### Tier A — built-in NLP embedding (no AI Core, immediate)
Proves `VECTOR_EMBEDDING` end-to-end with zero new privileges:
```sql
SELECT VECTOR_EMBEDDING('Hello world!', 'DOCUMENT', 'SAP_GXY.20250407') FROM DUMMY;
```
Run as the container `_RT` user via a `tutorials-hana` service key
(hana-cli / `@sap/hana-client`). Expected: a 768-dim `REAL_VECTOR`.

### Tier B — AI Core remote source (the issue's actual target)

**B1. Declarative privilege grant.** Extend `db/src/_grants.hdbgrants`
(the file that already grants `SPARQL QUERY/UPDATE` via the
`tutorials-kg-grantor` UPS) with the one missing system privilege, under
both `application_user` and `object_owner`: **`CREATE PSE`**. Applied by
`tutorials-db-deployer` on deploy. (`CREATE REMOTE SOURCE` is already
held — see confirmed facts.)

> **Deploy-time risk (try-first, per decision):** the grant only succeeds
> if the `tutorials-kg-grantor` grantor identity holds `CREATE PSE` **WITH
> ADMIN OPTION**. SPARQL privileges were delegable; `CREATE PSE` may not
> be. **Failure signature at deploy:** the `tutorials-db-deployer` task
> fails with a grant/insufficient-privilege error naming `CREATE PSE`.
> **Fallback:** a one-time admin grant of `CREATE PSE` WITH ADMIN OPTION
> to the grantor user (or `CREATE PSE` directly to the `_RT` container
> user), then re-deploy. Runbook documents both.

**B2. PSE + remote source SQL** (verbatim shape from the HANA Vector
Engine Guide "Connecting to SAP AI Core", mapped to our values):
```sql
CREATE PSE TUTORIALS_AICORE_PSE;
ALTER PSE TUTORIALS_AICORE_PSE SET OWN CERTIFICATE '
<RSA PRIVATE KEY from hana-ai-core key.pem, real line breaks>
<CLIENT CERTIFICATE from hana-ai-core cert.pem>
';

CREATE REMOTE SOURCE TUTORIALS_AICORE ADAPTER "sapgenaihub" CONFIGURATION
  'aiApiUrl=https://api.ai.prod.eu-central-1.aws.ml.hana.ondemand.com;
   authUrl=https://tutorial-system.authentication.cert.eu10.hana.ondemand.com;
   resourceGroup=default;
   deploymentId=da6d9c5e3fb50c3d;
   clientId=sb-78c0840a-3613-4a19-be4f-5cd52760090e!b676072|aicore!b540'
WITH CREDENTIAL TYPE 'X509' PSE TUTORIALS_AICORE_PSE;
```
Open question for the runbook: whether the PSE/remote source are best
created as container design-time artifacts (`.hdbpse` / grants) or as a
bootstrap SQL step run as the `_RT` user once privileges land. Default
call: bootstrap SQL first to prove it, then convert to design-time
artifacts as a follow-up so it survives container rebuilds. Flagged as my
call, revisit in the runbook.

**B3. Proof queries:**
```sql
CALL GET_REMOTE_SOURCE_AI_MODELS('TUTORIALS_AICORE', ?);  -- lists embedding models
SELECT VECTOR_EMBEDDING('Hello world!', 'DOCUMENT',
  'text-embedding-3-small.1', TUTORIALS_AICORE) FROM DUMMY;  -- model from B3 list
```

### Secrets handling
The x509 cert+key live only in the `hana-ai-core` service key. For PSE
creation they are pasted into `ALTER PSE ... SET OWN CERTIFICATE`. They
must **not** be committed to the repo. The runbook instructs pulling them
at setup time via `cf service-key tutorials-aicore hana-ai-core`.
Consider rotating `hana-ai-core` after setup if the key JSON was exposed
in any shared transcript.
