# `@cap-js/attachments` Programmatic Write/Read + Anonymous Serve — Spike Findings

- **Date:** 2026-08-17
- **Plugin version:** `@cap-js/attachments` **4.0.0** (CAP Node 10.0.5, `@cap-js/sqlite` 3.0.2)
- **Method:** SQLite in-memory round-trip + full source read of `lib/generic-handlers.js`, `srv/attachments/basic.js`, `srv/attachments/aws-s3.js`, `lib/plugin.js`, `db/index.cds`

## 1. CDS Model

```cds
using { Attachments } from '@cap-js/attachments';

entity TutorialImages {
  key sourceUrl : String;
  content       : Composition of one Attachments;
  // ...other fields
}
```

The generated attachments entity name is `<namespace>.TutorialImages.content` (composition element name becomes the suffix, always).

### Field names on the generated Attachments entity

| Field      | Type          | Notes                                        |
|------------|---------------|----------------------------------------------|
| `ID`       | UUID (key)    | Always present; generated by plugin          |
| `up__ID`   | FK            | Auto-generated back-ref to parent key (e.g. `up__sourceUrl` if parent key is `sourceUrl`) |
| `content`  | LargeBinary   | The bytes; `@Core.MediaType: mimeType`       |
| `mimeType` | String        | NOT `contentType`, NOT `mediaType`           |
| `filename` | String        | NOT `fileName` (lowercase `n`)               |
| `url`      | String        | Object-store key (a UUID); hidden from UI    |
| `hash`     | String        | SHA-256; computed after put                  |
| `status`   | String        | Default: `'Unscanned'`; scan gate uses this  |

## 2. Programmatic Write — Exact Call

### Obtain a linked entity (required for `put()`)

```js
const linked = cds.linked(cds.model)
const AttachmentsEntity = linked.definitions['<ns>.TutorialImages.content']
```

`cds.model.definitions[name]` returns an unlinked entity object with no `.name` property — CQL operations (`UPSERT`, `SELECT`) reject it. Always use `cds.linked(cds.model).definitions[name]`.

### Write via `AttachmentsSrv.put()` — **VERIFIED WORKING** on DB backend

```js
const AttachmentsSrv = await cds.connect.to('attachments')

await AttachmentsSrv.put(AttachmentsEntity, {
  ID:       cds.utils.uuid(),       // attachment row key
  url:      cds.utils.uuid(),       // object-store key (UUID) — required
  up__ID:   parentRecordKey,        // FK back to TutorialImages row
  content:  buffer,                 // Buffer (DB backend) OR Readable.from(buffer) (Object Store backend)
  mimeType: 'image/png',            // field name is `mimeType`
  filename: 'test.png',             // field name is `filename` (lowercase n)
  status:   'Clean',                // skip malware gate; set manually when scan=false
})
```

**DB backend (SQLite / HANA DB storage):** `content` can be a `Buffer` — empirically verified.

**Object Store backend (S3/Azure/GCP):** `content` MUST be a `Readable` stream; the S3 `put()` override checks `if (!content || !content.on)` and silently drops a non-stream. Wrap: `Readable.from(buffer)` for universal compatibility.

**Universal safe form (works on both backends):**
```js
const { Readable } = require('stream')
const content = Readable.from(imageBytes) // imageBytes is a Buffer
```

### Write via raw `UPSERT` (alternative, bypasses scan + overwrite check)

```js
await UPSERT({
  ID: attachmentId, url: cds.utils.uuid(), up__ID: parentKey,
  content: buffer, mimeType: 'image/png', filename: 'img.png', status: 'Clean'
}).into('<ns>.TutorialImages.content')
```

Empirically verified. The entity name string works directly; no linked-model lookup needed.

## 3. Programmatic Read — Exact Call

### Via `AttachmentsSrv.get()` — returns a **`Readable` stream**

```js
const AttachmentsSrv = await cds.connect.to('attachments')
const stream = await AttachmentsSrv.get(AttachmentsEntity, { ID: attachmentId })
// stream is a Node Readable (on both SQLite/DB and S3)
```

- On SQLite / HANA DB: returns `Readable` (CAP wraps the LargeBinary column)
- On S3: returns `content.Body` from `GetObjectCommand` — also a `Readable`
- Returns `null` if no content stored

### Via raw `SELECT` — also returns a `Readable`

```js
const row = await SELECT.one.from('<ns>.TutorialImages.content')
  .where({ ID: attachmentId })
  .columns('content', 'mimeType')
// row.content is a Readable — do NOT call Buffer.from(row.content) directly
```

### To consume as a Buffer:

```js
async function streamToBuffer(stream) {
  const chunks = []
  for await (const chunk of stream) chunks.push(chunk)
  return Buffer.concat(chunks)
}
const buf = await streamToBuffer(stream)
```

### To pipe into an HTTP response (CAP handler pattern):

```js
srv.on('GET', 'image-source', async (req) => {
  const { sourceUrl } = req.query.SELECT.where[2] // or extract from req
  const meta = await SELECT.one.from('TutorialImages').where({ sourceUrl }).columns('contentId', 'mimeType')
  if (!meta) return req.reject(404)
  const stream = await AttachmentsSrv.get(AttachmentsEntity, { ID: meta.contentId })
  req.res.setHeader('Content-Type', meta.mimeType)
  stream.pipe(req.res)
})
```

## 4. Content-Type Field Name

`mimeType` — this is the field name in the CDS aspect AND the field to read for the HTTP `Content-Type` response header.

```js
const { mimeType } = await SELECT.one.from('<ns>.TutorialImages.content')
  .where({ ID: id }).columns('mimeType')
// Use: res.setHeader('Content-Type', mimeType)
```

## 5. Anonymous Serve Verdict

**Custom stream handler approach: YES, anonymous serve works cleanly.**

A service without `@requires` can serve attachment content to unauthenticated callers via a custom `on('READ')` / `on('GET')` handler that calls `AttachmentsSrv.get()` directly. This approach:
- Has no malware-scan gate (scan gate is in `readAttachment`, which only runs for the plugin's default OData media endpoint)
- Gives full control over HTTP response headers
- Is exactly the pattern the design requires for `GET /content/image-source`

**Plugin default OData media endpoint + anonymous service + `scan: false`:** Also works, but only if the attachment row has a non-null `status`. `validateAttachment` in `generic-handlers.js` always calls `getScanInfo` → `req.reject(404)` if `status === null`. With `scan: false`, `enforceScanPolicy` is skipped, but the null-status 404 still fires. Since we always write `status: 'Clean'` on ingest, this gate is not a problem in practice — but the custom handler is simpler and recommended.

**Conclusion:** Use a **custom CAP handler** on a service without `@requires`, calling `AttachmentsSrv.get()` and piping the stream. Do NOT rely on the plugin's auto-generated OData media endpoint for the `GET /content/image-source` use case.

## 6. Deviations from Plan's Task 3 `image-store.js` Code

### D1: `@Capabilities.UpdateRestrictions.NonUpdatableProperties` blocks content overwrite

The plugin's `sap.attachments.Attachments` aspect sets:
```cds
annotate Attachments with @Capabilities.UpdateRestrictions.NonUpdatableProperties: [content];
```

When `put()` is called for an attachment whose `ID` already has content, it throws `409 Conflict`. The image invalidation case (hash changed → update in place) requires one of:

**Option A** (recommended) — annotate the composition to allow overwrite:
```cds
annotate TutorialImages.content with
  @Capabilities.UpdateRestrictions.NonUpdatableProperties: [];
```

**Option B** — use `UPSERT` directly (bypasses the check entirely).

**Option C** — delete the old attachment row before re-inserting (more expensive).

### D2: `get()` returns a Readable, not a Buffer

`image-store.js` code that reads `content` as a Buffer must use `streamToBuffer(await AttachmentsSrv.get(...))` or consume via `stream.pipe()`.

### D3: Entity must be linked

Any code that does `const e = cds.model.definitions['<ns>.TutorialImages.content']` and passes `e` to `AttachmentsSrv.put(e, ...)` or `SELECT.from(e)` will fail in CAP 10 — the entity object has no `.name` property. Use `cds.linked(cds.model).definitions[name]` or pass the entity name string directly to CQL operations.

### D4: `filename` field name (not `fileName`)

The CDS aspect uses `filename` (all lowercase). Any code that writes `{ fileName: '...' }` will silently skip the field.

### D5: `url` field is required for `put()`

The `url` field is the object-store routing key. For DB backend it's unused but must be present (`put()` sets it to `cds.utils.uuid()` internally in the Fiori path; in the programmatic path the caller must set it). If `url` is omitted, S3 `put()` logs an error and returns without uploading. Always set `url: cds.utils.uuid()` when calling `put()` programmatically.

### D6: `Composition of one` vs `Composition of many`

The design uses `content: Composition of one Attachments` (a single attachment per image row). The plugin supports this; behavior is identical to `Composition of many`. The entity name pattern is the same: `<ns>.TutorialImages.content`.
