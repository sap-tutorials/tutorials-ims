# Phase 4.3 — Discovery Missions Design

**Date:** 2026-06-28
**Issue:** [#447](https://github.com/sap-tutorials/tutorials-ims/issues/447) (Phase 4.3 sub-phase)
**Parent spec:** [`2026-06-28-447-knowledge-graph-phase4-architecture.md`](./2026-06-28-447-knowledge-graph-phase4-architecture.md)
**Sibling specs:** [`2026-06-28-447-phase4.1-learning-journeys.md`](./2026-06-28-447-phase4.1-learning-journeys.md) · [`2026-06-28-447-phase4.2-blog-posts.md`](./2026-06-28-447-phase4.2-blog-posts.md)

## §1 Goal & scope

Phase 4.3 adds **SAP Discovery Center missions** as the third new graph node type under the Phase 4 chassis. Each mission links to the concepts it teaches via the `teaches` predicate, and surfaces the BTP services it uses as free-form string tags. Missions appear on concept landing pages ("Discovery missions teaching this") and in the tutorial-OP sidebar's `otherResources` section alongside learning journeys and blog posts.

**Major scoping decision: missions-only.** The arch spec bundled "Discovery missions + Trials" into Phase 4.3, but the brainstorm settled on missions-only. Trials are deferred — the chassis's `trial` IRI prefix + TTL slot stays reserved but unused. Rationale: trials don't have a clean separate endpoint on Discovery Center; manual curation has insufficient operational ROI for 4.3 timing.

### In scope

- Weekly cron ingesting Discovery missions from the SAP Developers MCP (`sap-devs-server` via `search_discovery`)
- `DiscoveryMissions` + `DiscoveryMissionConceptLinks` + `DiscoveryMissionServices` entities (Composition cascade)
- LLM-based extraction adapter (`discovery-mission-extract.js`) emitting two predicates: `teaches` (concepts) + free-form `usesServices` (BTP service names)
- Concept-page section "Discovery missions teaching this"
- Sidebar `otherResources` widening to include `discovery-mission` row type
- Telemetry: `kg.discovery_mission.linked_from_concept_page`, `kg.discovery_mission.linked_from_sidebar`
- Shared `categoryLabel` lookup (`srv/lib/discovery-mission-categories.js`) consumed by both Hugo frontmatter (`scripts/fetch-concepts.ts`) and neighborhood enrichment (`srv/knowledge-graph-service.js`)
- Implements `sap-devs-client.searchDiscovery` (scaffolded in Phase 4.1 as `throw 'not implemented'`)

### Out of scope (explicit non-goals)

- **Trials.** Deferred indefinitely; chassis slot remains reserved.
- **`usesService` FK to `Products`.** Free-form strings only; future evolution could promote to FK.
- **Mission completion tracking.** Discovery Center has its own progress mechanism.
- **Per-mission landing pages.** Following the 4.1/4.2 pattern — concept page + sidebar only.
- **Mission ordering predicates** (mission → mission prerequisites). Mission catalogs don't expose ordering metadata.

## §2 Design decisions

| ID | Decision | Rationale |
|---|---|---|
| Q1 | **Scope: missions-only; defer trials** | MCP doesn't expose a trials endpoint; trial mentions inside mission descriptions are heuristic-driven; manual curation is operational tax with insufficient ROI for 4.3 timing. Chassis slot remains reserved. |
| Q2 | **Source: `sap-devs` MCP `search_discovery`** | First sub-phase to actually wire the method (Phase 4.1 scaffolded it as `throw 'not implemented'`). Pattern mirrors `searchLearningJourneys` verbatim (in-process + on-disk cache, 6h TTL already declared in `TOOL_TTLS`, validator, `_setMockTransport` hook). |
| Q3 | **Predicates: `teaches` + free-form `usesServices`** | Missions teach hands-on skills (matches Tutorial's `teaches` semantic but on a separate link table). `usesServices` captures BTP services mentioned in descriptions (e.g. "SAP Integration Suite", "SAP Build Apps") as free-form strings — NOT FK to `Products`. Free-form keeps the cron cheap (no embedding per service mention), keeps the schema simple, and defers SQL-joinable "missions using HANA Cloud" queries to a future evolution. |
| Q4 | **TTL: 180 days (chassis-locked)** | `srv/lib/external-content-ttl.js` already declares `'discovery-mission': 180` per architecture spec. Mid-life-cycle; SAP refreshes mission catalogs ~quarterly. |
| Q5 | **Cadence: weekly Sunday 03:07 UTC** | Quarterly catalog refresh velocity makes daily overkill. Mirrors 4.1's cadence. Off-minute (`:07`) separates from existing crons at `:13` (journey) and `:23` (blog). |
| Q6 | **Backfill: none** | SAP's mission catalog is ~100-200 missions total; first cron run lands all in one cycle (page size 200). No "24-month historical window" concept since missions don't have a meaningful `createdAt`. |
| Q7 | **Effort + category captured + surfaced** | MCP returns `effort: '1'-'5'` (numeric-as-string) and `category` (short code: `onboard`, `intgn`, `develop`, etc.). Surfaced on concept page row (`· effort 2 · Onboarding`) and sidebar (`· effort 2 · Onboarding`). |
| Q8 | **`categoryLabel` resolution via static lookup** | MCP returns short codes only; English labels (`Onboarding`, `Integration`) aren't accessible via MCP. Hand-curated 8-entry table in `srv/lib/discovery-mission-categories.js`; title-case fallback for unknown slugs. Lookup imported by BOTH `scripts/fetch-concepts.ts` AND `srv/knowledge-graph-service.js` — single source of truth. |
| Q9 | **Budget gate: per-cycle (not per-day)** | `ChatSettings.discoveryMissionExtractBudgetPerCycle` (default 100). Weekly cadence means per-cycle aligns naturally. Same try/catch fall-through to default pattern as 4.1/4.2 (column doesn't get added to schema). |
| Q10 | **UI surfaces: concept page section + sidebar `otherResources` widening** | Identical to 4.1/4.2. Concept page section #4 (after Blog Posts, before Prerequisites). Sidebar `otherResources` rendering branch for `discovery-mission`. |

## §4 Schema (`db/external-content.cds`)

Append below Phase 4.2's `BlogPosts` block:

```cds
/**
 * Phase 4.3 (#447): SAP Discovery Center missions.
 *
 * - mcpId is the natural key (numeric `id` field from search_discovery, e.g. '3019').
 *   slug is derived as `dm-${mcpId}` for IRI namespace-safety.
 * - description is the mission's blurb captured at upsert time (matches 4.2's excerpt
 *   role — sidebar card needs it without re-fetching anything).
 * - effortLevel: 1-5 numeric (MCP returns as string; cron parseInt-coerces).
 * - categorySlug: short code from MCP (e.g. 'onboard', 'intgn'); label resolution
 *   happens at render time via srv/lib/discovery-mission-categories.js.
 * - pinUntil reserved for chassis uniformity; no admin surface writes it in 4.3.
 */
entity DiscoveryMissions : cuid, managed {
  slug              : String(120) @assert.unique;
  title             : String(400);
  description       : String(2000);
  url               : String(500);
  mcpId             : String(40);
  effortLevel       : Integer;
  categorySlug      : String(40);

  sourceId          : String(120);
  contentHash       : String(64);
  lastExtractedHash : String(64);
  firstSeenAt       : Timestamp @cds.on.insert: $now;
  lastSeenAt        : Timestamp;
  pinUntil          : Timestamp;

  links    : Composition of many DiscoveryMissionConceptLinks on links.mission = $self;
  services : Composition of many DiscoveryMissionServices    on services.mission = $self;
}

entity DiscoveryMissionConceptLinks : cuid, managed {
  mission      : Association to DiscoveryMissions @assert.notNull;
  concept      : Association to ims.Concepts     @assert.notNull;
  predicate    : String(20) default 'teaches';
  confidence   : Decimal(3, 2);
  extractedAt  : Timestamp;
  modelVersion : String(40);
}

entity DiscoveryMissionServices : cuid, managed {
  mission      : Association to DiscoveryMissions @assert.notNull;
  serviceName  : String(120);
  confidence   : Decimal(3, 2);
  extractedAt  : Timestamp;
  modelVersion : String(40);
}

annotate DiscoveryMissionConceptLinks with
  @assert.unique.missionConcept : [mission, concept];

annotate DiscoveryMissionServices with
  @assert.unique.missionService : [mission, serviceName];
```

### Build artifacts

After editing `db/external-content.cds`, run `cds build --production` and stage `db/last-dev/csn.json` + `db/src/*.hdbmigrationtable` in the same commit. Per the project's `feedback_cds_schema_plans_need_cds_build_production_step` convention; CI's `check-cds-build-staging` fails the PR otherwise.

### Case-sensitivity note on `@assert.unique.missionService`

CDS `@assert.unique` is **case-sensitive** on HANA. The cron's case-insensitive dedup at §7 step 6.g (`serviceName.toLowerCase()` collapse) is the canonical guard against `"SAP Build Apps"` vs `"sap build apps"` duplicates. The DB constraint catches exact-duplicate writes only. Future writers MUST preserve the case-insensitive cron-side dedup; relying on the DB constraint alone is insufficient.

### Slug derivation

`dm-${mcpId}`. MCP returns numeric IDs (5-7 digits in observed data: `3019`, `3258`, `3585`); stable across edits. Same pattern as 4.2's `bp-${khorosMessageId}`. `String(120)` is generous headroom matching the chassis precedent.

### Why `DiscoveryMissionServices` is a separate entity (not a string-array column)

- CDS arrays-of-strings generate clunky denormalised side-tables anyway. Better to control the shape explicitly.
- The cron's DELETE-then-INSERT pattern works cleanly per-entity (mirrors `BlogPostConceptLinks`).
- `@assert.unique.missionService` prevents a mission from listing the same service twice.
- `confidence` lets us drop weakly-asserted service tags (floor 0.7 — higher than concept-teaches because service names are easier to over-emit).
- Future evolution: if "missions using HANA Cloud" SQL queries become valuable, this table is the natural place to add an FK to `Products`.

### Asymmetries with previous sub-phases (deliberate)

1. **Two link tables, not one.** First sub-phase to model two predicates as separate tables. Polymorphic single-table with discriminator would have required CDS hackery; clean two-table approach is more maintainable.
2. **`description` is wider (2000 vs blog's 1000).** Mission descriptions run multi-paragraph; project's existing `Tutorials.description` uses 4000, so 2000 is a middle ground.
3. **No `author*` columns.** Missions are SAP-curated; no person attribution surface.
4. **`effortLevel` is Integer**, parsed from MCP's numeric-as-string at cron-write time.

### Validator

Throws on missing/wrong-typed fields:

- `id: string` (numeric, but string-safe — MCP returns as string)
- `name: string` (the title)
- `effort: string` (numeric-as-string; coerced to Integer at cron-write time)
- `category: string` (short code; never empty in practice but validator just checks non-undefined)
- `description: string`

### URL synthesis

MCP doesn't return a `url` field. Synthesised at cron-write time per §7 step 5.d: `https://discovery-center.cloud.sap/missiondetail/${m.id}/`. Verified format from real Discovery Center URLs.

## §6 Extraction adapter (`srv/lib/discovery-mission-extract.js`)

Mirrors `blog-post-extract.js` with these differences:

- **System prompt:** "You are extracting concepts from an SAP Discovery Center mission. Missions teach hands-on skills via curated end-to-end scenarios. Identify (a) the technical concepts the mission TEACHES, and (b) the SAP BTP services the mission USES. Missions are broader than blog posts but more focused than learning journeys."
- **LLM schema:** `{ teaches: [{slug, name, confidence}], usesServices: [{name, confidence}] }`. Two predicates.
- **Post-LLM validation:**
  - `teaches`: floor 0.6, cap 8, name required (defends against LLM drift)
  - `usesServices`: floor 0.7 (higher — service names are easier to over-emit), cap 5, name required, name length ≥ 2 chars
  - Slug regex: same `^[a-z0-9][a-z0-9-]{0,78}[a-z0-9]$` as 4.1/4.2

## §7 Cron orchestration (`srv/jobs/fetch-discovery-missions-job.js`)

Schedule: `'7 3 * * 0'` (Sunday 03:07 UTC, off-minute). Registered in `srv/jobs/scheduler.js` after the existing journey + blog crons. Well-separated from existing weekly crons (`:07` vs journey's `:13`).

### Per-cycle flow

```text
1. Read ChatSettings.discoveryMissionExtractBudgetPerCycle (default 100).
   If <= 0, exit clean. Test seam: deps.budgetOverride.
2. Load merge config (mergeSimThresholdExtract from KG, embeddingModel from ChatSettings).
3. Load concept registry once: loadConceptRegistry(db).
4. No sinceIso gate. MCP doesn't expose per-mission modifiedAt; we refetch the full
   ~100-200 catalog every Sunday and rely on contentHash-based step 5d to skip
   unchanged missions.
5. Fetch from MCP via searchDiscovery({type: 'missions', limit: 200}).
   For each mission:
     a. Derive slug = `dm-${m.id}`.
     b. effortLevel = parseInt(m.effort, 10); fallback null on NaN.
     c. contentHash = sha256(name + description + effort + category).
     d. Upsert DiscoveryMissions row (chassis pattern). url synthesised at write time:
        `url: m.url || \`https://discovery-center.cloud.sap/missiondetail/${m.id}/\``
        (prefer MCP value if it ever starts being returned; otherwise synthesise).
     e. needsExtraction = !existing || existing.lastExtractedHash !== contentHash.
6. For each in extractQueue (bounded by budget):
   **Invariant:** step 6.i (the `lastExtractedHash` UPDATE) is the final write in the per-mission sequence. Any failure before 6.i leaves the mission re-queueable on the next cycle (the `lastExtractedHash` stays at its previous value → `needsExtraction` re-fires). See #708 chassis pattern.
   - extractConceptsFromDiscoveryMission(mission, nearestConcepts) →
     {teaches, usesServices, tokenUsage}
   - resolveConceptCandidates({candidates: teaches, registry, embed, ...}) →
     resolved + pendingMints + counters
   - In sequence (no explicit tx, autocommit per INSERT):
     a. INSERT pendingMints into Concepts (FK targets first).
     b. Warm registry with new mints.
     c. DELETE existing DiscoveryMissionConceptLinks where mission_ID = this.
     d. Dedup resolved by conceptId (highest-confidence wins).
     e. INSERT new DiscoveryMissionConceptLinks.
     f. DELETE existing DiscoveryMissionServices where mission_ID = this.
     g. Dedup usesServices by serviceName.toLowerCase() (case-insensitive).
     h. INSERT new DiscoveryMissionServices rows (NO merge-on-write).
     i. UPDATE DiscoveryMissions SET lastExtractedHash = contentHash
        (#708 crash-safety; FINAL step).
   - summary.extracted++; merge counters from resolution.
7. Log summary.
```

### Summary shape

```javascript
{
  fetched: 0,             // missions seen from MCP
  upserted: 0,            // rows touched in DiscoveryMissions
  extracted: 0,           // LLM calls made
  skippedNoChange: 0,
  mergedAtExtract: 0,     // #707 — concept slugs fuzzy-merged
  mintedAtExtract: 0,     // #707 — fresh concepts minted
  skippedNoEmbed: 0,
  teachesWritten: 0,      // DiscoveryMissionConceptLinks rows INSERTed
  servicesWritten: 0,     // DiscoveryMissionServices rows INSERTed
  promptTokens: 0,
  completionTokens: 0,
  errors: 0,
  budgetExhausted: false,
}
```

### Failure modes (mirrors 4.2 §7.1)

| Failure | Cron behavior |
|---|---|
| MCP 5xx mid-fetch | Abort cycle. `summary.errors++`. Already-upserted rows stay. |
| MCP rate-limit (429) | Same — abort + log + retry next cycle. |
| Validator throws on a bad row | Skip the row, `summary.errors++`, continue. |
| LLM extract throws mid-queue | Skip that mission; `summary.errors++`; continue. |
| Budget exhausted mid-queue | Break + `budgetExhausted: true`. Deferred missions' `lastExtractedHash` stays at prior value; re-extract next cycle. |
| Partial failure between 6.a and 6.i | `lastExtractedHash` not yet updated → next cycle re-fires 6 → DELETE-then-INSERT replaces partial state. Orphan Concepts from prior partial run get reused via merge-on-write or eventually GC'd by `consolidateConcepts`. Harmless. |

### Backend payload (`srv/lib/published-concepts-query.js`)

Adds a sibling array per concept:

```javascript
const { DiscoveryMissions, DiscoveryMissionConceptLinks } =
  cds.entities('com.sap.developers.ims.external');

if (conceptIds.length === 0) {
  for (const c of concepts) c.discoveryMissions = [];
} else {
  const missionLinks = await SELECT.from(DiscoveryMissionConceptLinks)
    .columns(
      'concept_ID',
      'mission.slug as missionSlug',
      'mission.title as title',
      'mission.url as url',
      'mission.effortLevel as effortLevel',
      'mission.categorySlug as categorySlug',
    )
    .where({ concept_ID: { in: conceptIds } })
    .orderBy('mission.effortLevel asc')   // easier missions first
    .limit(8 * conceptIds.length);

  // Group + 8-row cap per concept (matches 4.2's blogPosts shape).
}
```

**Ordering rationale:** `effortLevel asc` surfaces easier missions first per concept. A user landing on a concept page is more likely to want low-friction entry points than the deepest end-to-end mission.

### Neighborhood enrichment (`srv/knowledge-graph-service.js`)

Phase 4.2 already widened `otherResources` to UNION journey + blog. Phase 4.3 adds a third branch parallel to the existing two:

```javascript
// Phase 4.3 (#447): discovery-mission overlap rows.
const { DiscoveryMissions, DiscoveryMissionConceptLinks } =
  cds.entities('com.sap.developers.ims.external');

let missionOtherResources = [];
if (conceptIds.length > 0) {
  const missionOverlaps = await SELECT.from(DiscoveryMissionConceptLinks)
    .columns('mission_ID', 'concept_ID')
    .where({ concept_ID: { in: conceptIds } });

  const overlapByMission = new Map();
  for (const row of missionOverlaps) {
    overlapByMission.set(row.mission_ID, (overlapByMission.get(row.mission_ID) ?? 0) + 1);
  }

  if (overlapByMission.size > 0) {
    const topMissionIds = [...overlapByMission.entries()]
      .sort(([, a], [, b]) => b - a)
      .slice(0, MAX_OTHER_RESOURCES)
      .map(([id]) => id);

    const missions = await SELECT.from(DiscoveryMissions)
      .columns('ID', 'slug', 'title', 'url', 'effortLevel', 'categorySlug')
      .where({ ID: { in: topMissionIds } });

    const byMissionId = new Map(missions.map((m) => [m.ID, m]));
    missionOtherResources = topMissionIds
      .map((id) => byMissionId.get(id))
      .filter(Boolean)
      .map((m) => ({
        type: 'discovery-mission',
        slug: m.slug,
        title: m.title,
        url: m.url,
        effortLevel: m.effortLevel,
        categoryLabel: categoryLabel(m.categorySlug),   // shared helper
        overlapCount: overlapByMission.get(m.ID),
      }));
  }
}

// Merge journey + blog + mission rows; top-5 TOTAL across types.
const otherResources = mergeOtherResources([
  ...journeyOtherResources,
  ...blogOtherResources,
  ...missionOtherResources,
]);
```

The `mergeOtherResources` helper from Phase 4.2 (`srv/lib/kg-neighborhood-merge.js`) already sorts by `overlapCount` desc and caps to `MAX_OTHER_RESOURCES = 5`. Phase 4.3 just feeds it the third array. **No changes to the helper itself.**

### CDS `NeighborhoodResult.OtherResource` type

`srv/knowledge-graph-service.cds`: extend with `effortLevel : Integer;` + `categoryLabel : String;` (both optional in CDS query-type semantics — null for non-discovery-mission rows). The existing 9-field type (extended by Phase 4.2) becomes an 11-field type.

### Acceptance criteria

1. **First cron run lands the catalog.** Sunday after deploy:
   - `DiscoveryMissions` ≥ 100 rows (the full catalog upserts in one cycle — step 5 is NOT budget-gated, only LLM extraction is).
   - `DiscoveryMissionConceptLinks` ≥ 60 rows (budget=100 missions/cycle × ~2-3 surviving teaches concepts ≈ 200-300 link rows; the 60-row floor assumes a worst-case 50% partial-cycle scenario).
   - Catalog upsert completes in one cycle (~100-200 rows). LLM extraction (concept + service links) completes over **1-2 cycles** depending on catalog size vs `budget=100`. An operator looking at row counts after Week 1 should expect partial extraction coverage; Week 2 closes the gap.

   *Basis:* MCP-probe-time data showed 12 missions matched query `"trial"`; broader queries return more. Arch spec §3.4 sizes the full catalog at ~100-200 missions. Phase 4.1/4.2 extraction yielded ~2-3 covers/source at LLM floor 0.6; for `teaches` predicate on missions (floor 0.6, cap 8), ~3 is the conservative middle.

2. **Weekly cron idempotent.** Two consecutive Sunday runs with no upstream changes: `summary.skippedNoChange == fetched`.

3. **Crash-safety holds.** Test-only abort signal between `DELETE links` and `INSERT links` leaves `lastExtractedHash` at its previous value; next cycle re-extracts.

4. **Concept pages render.** A test concept's page on the DEV approuter shows a non-empty "Discovery missions teaching this" section after the first cron has run and content has been published. Rows display `· effort N · CategoryLabel`.

5. **Sidebar shows mission rows.** Tutorial-OP sidebar shows at least one `discovery-mission` row when a tutorial's concepts overlap with at least one indexed mission. Top-5 ranking is across all three content types (journey + blog + mission), not per-type.

6. **Telemetry events fire** on click in both surfaces (`kg.discovery_mission.linked_from_concept_page`, `kg.discovery_mission.linked_from_sidebar`).

7. **Merge-on-write reuses #707.** A mission mentioning a novel concept slug ends up in `Concepts` either as merged-or-minted; `skippedNoEmbed` counts only embed failures.

8. **`usesServices` dedup case-insensitive.** A mission description naming "SAP Integration Suite" twice (or "sap integration suite" + "SAP Integration Suite") collapses to one row in `DiscoveryMissionServices`.

### LLM cost basis

100 missions/cycle × (~3.5K input + ~500 output tokens) at gpt-4o-mini rates (~$0.150 / 1M input, $0.600 / 1M output as of 2026-06):

`100 × (3500 × 0.00000015 + 500 × 0.0000006) ≈ 100 × 0.000825 ≈ $0.08 per weekly cycle`

= ~$4 / year steady-state. Well under operational noise floor.

Embedding cost: ~5-15 novel concepts minted per cycle (estimate based on 4.1/4.2 backfill ratios) × 1 embed call × text-embedding-3-small ($0.00002 / 1K tokens) ≈ $0.0001 / cycle. Negligible.

Same provider + model as 4.1/4.2. No new infrastructure.
