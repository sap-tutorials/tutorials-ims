# cds-caching UPSERT Fix (#3102) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stop `cds-caching` from logging `error`-level unique-constraint-violation noise in PROD when two HA instances concurrently write the same cache key (notably `kg:rl:*` rate-limiter counters), by making the `KeyvCDS.set()` write path an atomic single-key UPSERT.

**Architecture:** The defect lives in the vendored `cds-caching` plugin (`node_modules/cds-caching/lib/support/KeyvCDS.js`), whose `set()` does read-then-`create`/`update` — a TOCTOU race that collides on the `CacheStore` PK under multi-instance CF. We fix it two ways: (1) **locally and immediately** via a committed `patch-package` patch against our pinned `cds-caching@2.1.0`, replacing the racy branch with `UPSERT.into(entity).entries(...)` (last-write-wins, no collision); (2) **upstream** by filing an issue + PR against `mikezaschka/cds-caching` so the patch can eventually be dropped. The bug is confirmed still present on upstream `main`.

**Tech Stack:** Node.js 22, `@sap/cds` (CQL `UPSERT`), `cds-caching@2.1.0`, `patch-package`, HANA (prod/hybrid) / SQLite (unit).

**Spec:** GitHub issue [sap-tutorials/tutorials-ims#3102](https://github.com/sap-tutorials/tutorials-ims/issues/3102)

## Global Constraints

- `cds-caching` is pinned at exactly `"2.1.0"` in `package.json` dependencies — the patch filename and `patch-package` match this version verbatim; do **not** bump it as part of this fix.
- Node engine is pinned `22.23.4`; `patch-package` must run under it.
- No raw SQL — use CQL `UPSERT` (`@sap/cds`), consistent with the CAP constraint in CLAUDE.md.
- The `CacheStore` entity is single-PK: `key ID : String(900); value : LargeString; expiresAt : Int64;`. UPSERT semantics are only safe here because the key is a single PK column (composite-key UPSERT on HANA via CDS QL is a known gotcha — not applicable).
- The fix must remain **fail-open**: `set()` must still never throw to its caller (keep the existing `try/catch` returning normally).
- `patch-package` must re-apply automatically on `npm ci` / `npm install` (CI uses `npm ci`), via a `postinstall` hook, without breaking the existing `prepare` script.
- The MCP MTA (`tutorials-mcp`) and QA app reuse the same `srv/lib` tree but **not** `node_modules` patching concerns — no `srv-qa` cp-list change is needed (no new `srv/lib/` file).

## Review Focus

- **npm script collision:** the repo has `prepare` (git hooks) but no `postinstall`. Adding `postinstall: patch-package` must not clobber `prepare`; both must run on install. — covered in Task 2 (verify `npm ci` output shows both hooks firing).
- **Patch fails to apply after a future `cds-caching` bump:** `patch-package` errors (non-zero) if the target file drifted. Task 2 pins the exact `2.1.0` and documents the drop-on-upgrade path; the drift surfaces loudly at install, not silently.
- **UPSERT on SQLite (unit profile):** unit tests use in-memory SQLite with `store:"memory"` (not `cds`), so KeyvCDS is never exercised there; the patch's UPSERT path is only hit under `store:"cds"`. Task 1 adds a direct KeyvCDS test against an in-memory SQLite db to prove UPSERT works on *both* dialects and that a double-set of the same key does not throw.
- **`value`/`expiresAt` null handling:** a `set` with no TTL stores `expiresAt: null`; UPSERT must preserve that (not drop the column). Task 1 asserts a re-set with a shorter/absent TTL overwrites cleanly.
- **Concurrent set does not lose the row entirely:** after two racing sets, the key must still be readable (one winner), never left absent. Task 1 asserts the key exists post-double-set.

- [ ] **Step 1: Write the failing test**

Create `srv/lib/__tests__/keyv-cds-upsert.test.js`. It instantiates the real `KeyvCDS` class from `cds-caching`, backed by an in-memory SQLite `cds.db` with the `plugin.cds_caching.CacheStore` entity deployed, and asserts the collision-safe contract:

```js
import { describe, it, expect, beforeAll } from 'vitest';
import cds from '@sap/cds';
import KeyvCDS from 'cds-caching/lib/support/KeyvCDS.js';

describe('KeyvCDS.set is collision-safe (issue #3102)', () => {
  beforeAll(async () => {
    // deploy only the cache-store entity into an in-memory sqlite db
    cds.model = await cds.load([require.resolve('cds-caching/db/cache-store.cds')]);
    await cds.deploy(cds.model).to('sqlite::memory:');
  });

  it('a second set of the same key does NOT throw and overwrites (last-write-wins)', async () => {
    const store = new KeyvCDS({});
    await store.set('dup', { count: 1 }, 10_000);
    await expect(store.set('dup', { count: 2 }, 10_000)).resolves.not.toThrow();
    expect(await store.get('dup')).toEqual({ count: 2 });
  });

  it('two concurrent sets of a fresh key both resolve and the key is present', async () => {
    const store = new KeyvCDS({});
    await Promise.all([store.set('race', { a: 1 }, 10_000), store.set('race', { a: 2 }, 10_000)]);
    expect(await store.get('race')).toBeDefined();
  });

  it('re-set with no TTL overwrites cleanly (expiresAt null)', async () => {
    const store = new KeyvCDS({});
    await store.set('nt', 'first', 10_000);
    await store.set('nt', 'second'); // no ttl
    expect(await store.get('nt')).toBe('second');
  });
});
```

The decisive assertion is that a simulated collision does not surface. (On SQLite a true PK re-INSERT would throw `UNIQUE constraint failed`; the pre-patch read-then-create code path can hit it under interleaving. Post-patch UPSERT never does.)

- [ ] **Step 3: Edit `node_modules/cds-caching/lib/support/KeyvCDS.js`**

Replace the body of `async set(key, value, ttl)` so the read-then-`create`/`update` branch becomes a single atomic UPSERT, keeping the outer `try/catch` (fail-open, no re-throw) intact:

```js
async set(key, value, ttl) {
    try {
        const { db, entity } = await this._getDB();
        if (!db || !entity) return;
        const expiresAt = ttl ? Date.now() + ttl : null;
        // Atomic last-write-wins. CacheStore has a single-column PK (ID),
        // so UPSERT compiles to HANA `UPSERT ... WITH PRIMARY KEY` and to
        // SQLite `INSERT OR REPLACE` — no read-then-write race, no unique
        // constraint collision under multi-instance concurrency (#3102).
        await db.run(UPSERT.into(entity).entries({ ID: key, value, expiresAt }));
    } catch (error) {
        this.log.error(`KeyvCDS set error for key ${key}:`, error);
    }
}
```

`UPSERT` is a CQL global provided by `@sap/cds`; `cds` is already required at the top of the file (`const cds = require('@sap/cds')`), and `UPSERT` is exposed as a global by the cds runtime. If `UPSERT` is not in scope in this module, reference it as `cds.ql.UPSERT`. Confirm which form resolves before generating the patch.
