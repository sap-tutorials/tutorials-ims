# CAP 10.2 Upgrade Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Upgrade all CAP and CAP plugin packages from 10.1.x to 10.2.x, and opt into new 10.2 features where beneficial.

**Architecture:** This is a dependency-bump upgrade. Core changes are: bump `@sap/cds` and `@sap/cds-dk` to `^10.2.0`, bump all `@cap-js/*` plugins to their latest 10.2-compatible versions, relax the `@cap-js/ai` tilde pin to `^1.3.0`, and evaluate three opt-in flags (`draft_admin_integrity`, `draft_orphan_cleanup`, and the new `@cds.autoexpose: false` for internal services). No schema changes are required; no Java dependencies in this project.

**Tech Stack:** Node.js 22.23.4, `@sap/cds` ^10.2.x, CAP plugin ecosystem, SQLite (dev/test), HANA Cloud (hybrid/prod)

**Spec:** https://cap.cloud.sap/docs/releases/2026/oct26

## Global Constraints

- Node.js 22.23.4 — pinned exactly in `engines.node`; do NOT change this
- All CAP Node.js only — no Java migration steps apply
- Tests must pass: `npm test` (in-memory SQLite, fast); hybrid tests are out-of-scope for this PR
- Never write raw SQL — use `cds.ql` or CQL
- PR targets `DEV` branch (never `main`)
- `@cap-js/graphql` is currently pinned to `0.14.0` (exact, no caret); only bump if a new release is available
- `@cap-js/attachments` is currently pinned to `4.0.0` (exact); only bump if a new release is available
- `@cap-js/data-inspector` is currently pinned to `1.0.5` (exact); only bump if `2.0.1` is confirmed for this ecosystem
- The `mcp.per_action_tool: true` config remains in place — the "single `call` tool" 10.2 default does not apply here since we intentionally override it

## Review Focus

- `@cap-js/ai` version jump from `~1.1.0` to `^1.3.0` spans two minor versions: verify AI-author (ValueList recommendations), ONNX model initialization, and `AICore-mocked` local mode still work after bump
- `cds.fiori.draft_admin_integrity: true` changes which delete handlers are called on draft entities — verify that `AdminService` draft entities (`Tutorials`, `Missions`, `Groups`, etc.) still delete cleanly and that any custom `@before DELETE` handlers are not skipped
- `draft_orphan_cleanup` is a new background job; verify it does not interfere with the CAP scheduler / `CronService` under `cds watch` or unit tests
- `@cap-js/change-tracking` bumped to 2.2.3 — verify that change tracking on `TutorialMeta` and related entities still works and that tracked payloads in tests match expected structure
- `@sap/cds` 10.2.x removes `@odata.metadataEtag` from default responses; the `./test/` suite may assert on response shapes — scan for any assertion on `@odata.metadataEtag` and update or remove

## Task 3: Evaluate and adopt opt-in 10.2 flags

**Files:**
- Modify: `package.json` (`.cds` block → `fiori` section)

**Interfaces:**
- Consumes: Task 2 (all plugins at 10.2 versions)
- Produces: `package.json` CDS config updated with evaluated opt-in flags

The three 10.2 opt-ins to evaluate:

1. **`cds.fiori.draft_admin_integrity: true`** — draft deletion uses DB cascades; only matters if draft entities have custom delete handlers. Search before adopting.
2. **`cds.fiori.draft_orphan_cleanup: true`** — background cleanup of orphaned draft rows; safe to adopt.
3. **`@cds.autoexpose: false`** annotation — prevents entity duplication in exported APIs; applies to CDS model files, not `package.json`.

- [ ] **Step 1: Check for custom draft delete handlers**

```bash
grep -rn "DELETE\|draft.*delete\|delete.*draft" srv/ --include="*.js" | grep -i "before\|on\|after" | head -20
```

If any handler targets draft entities with custom logic, skip `draft_admin_integrity` for now and note it in the commit message.

- [ ] **Step 2: Adopt `draft_orphan_cleanup`**

In the `cds.fiori` section of `package.json` (create it if absent):

```json
"fiori": {
  "draft_orphan_cleanup": true
}
```

- [ ] **Step 3: Conditionally adopt `draft_admin_integrity`**

If Step 1 found no custom draft delete handlers, add to `cds.fiori`:

```json
"draft_admin_integrity": true
```

If custom handlers found, skip and add a comment in the PR description explaining why.

- [ ] **Step 4: Run unit tests to verify draft behavior unchanged**

```bash
npm test -- --grep "draft" 2>&1 | tail -30
```
Expected: tests related to drafts pass; if `draft_admin_integrity` causes failures, revert only that flag.

- [ ] **Step 5: Run the full test suite**

```bash
npm test 2>&1 | tail -40
```
Expected: all tests pass

- [ ] **Step 6: Commit**

```bash
git add package.json
git commit -m "feat(cap): adopt CAP 10.2 draft opt-in flags (orphan_cleanup[, admin_integrity])"
```
