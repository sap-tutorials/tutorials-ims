# Events.eventType Enum — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a closed `eventType` enum column to the `Events` entity (values: `DEVTOBERFEST`, `TECHED`, `CODEJAM`, `CHALLENGE`, `OTHER`, default `OTHER`), surface it in the admin UI, analytics, and the public API, and back-populate every existing row to `OTHER` via the standard HDI migration.

**Architecture:** Pure CAP-level `String(20) enum` with `@assert.range` — same machinery as the existing `MissionType` on `Missions`. The HDI migration adds the column with `DEFAULT 'OTHER'`, which back-populates every existing row in one ALTER. Fiori Elements renders an inline dropdown via `@Common.ValueListWithFixedValues` because the enum members ARE the fixed value list — no `EventTypes` reference table.

**Tech Stack:** CAP Node.js (CDS) · SAP HANA Cloud (HDI) · Fiori Elements V4 · vitest (unit) · `cds.test` HTTP harness.

**Spec:** [docs/superpowers/specs/2026-06-26-event-type-design.md](../specs/2026-06-26-event-type-design.md)
**Issue:** [#646](https://github.com/sap-tutorials/ims/issues/646)
**Branch:** `worktree-feat-646-event-type` (worktree at `.claude/worktrees/feat-646-event-type`)

## Task 3 — Add the failing test for default/range behavior (TDD red)

**Files:**
- Create: `test/unit/event-type.test.js`

Write the test before the rest of the wiring so the platform-level enum behavior is anchored first. This test exercises the in-memory SQLite path and verifies (a) the default fires, (b) a valid enum value is accepted, (c) an invalid value is rejected.

- [ ] **Step 3.1 — Create the test file**

  Write the following content to `test/unit/event-type.test.js`:

  ```javascript
  import { describe, it, expect, beforeAll } from 'vitest';
  import cds from '@sap/cds';

  // Boot a tiny in-memory CAP service with the project's full model.
  // Same pattern as test/developer-service.test.js:4 — keeps test isolation
  // by giving us our own SQLite db with the freshly-deployed schema.
  cds.test('serve', '--project', '.', '--in-memory');

  describe('Events.eventType enum', () => {
    let Events;

    beforeAll(() => {
      Events = cds.entities('com.sap.developers.ims').Events;
    });

    it("defaults to 'OTHER' when not specified on INSERT", async () => {
      const ID = 'evt-default-test-0001';
      await INSERT.into(Events).entries({
        ID,
        legacyId: 990001,
        name: 'Default Test Event',
        startDate: '2026-01-01T00:00:00Z',
        endDate: '2026-01-02T00:00:00Z',
        timeZone: '+00:00'
      });
      const row = await SELECT.one.from(Events).where({ ID });
      expect(row.eventType).toBe('OTHER');
    });

    it('accepts every declared enum value', async () => {
      const values = ['DEVTOBERFEST', 'TECHED', 'CODEJAM', 'CHALLENGE', 'OTHER'];
      for (const v of values) {
        const ID = `evt-valid-${v.toLowerCase()}`;
        await INSERT.into(Events).entries({
          ID,
          legacyId: 990100 + values.indexOf(v),
          name: `Valid ${v}`,
          startDate: '2026-01-01T00:00:00Z',
          endDate: '2026-01-02T00:00:00Z',
          timeZone: '+00:00',
          eventType: v
        });
        const row = await SELECT.one.from(Events).where({ ID });
        expect(row.eventType).toBe(v);
      }
    });

    it('rejects an out-of-range value via @assert.range', async () => {
      // @assert.range surfaces as a SERVICE-level guard, not a DB-level one,
      // so a direct INSERT.into bypasses it. Exercise via a service request
      // through the AdminService projection instead.
      const AdminService = await cds.connect.to('AdminService');
      await expect(
        AdminService.send({
          query: INSERT.into('AdminService.Events').entries({
            ID: 'evt-bad-range-0001',
            legacyId: 990999,
            name: 'Bad Range',
            startDate: '2026-01-01T00:00:00Z',
            endDate: '2026-01-02T00:00:00Z',
            timeZone: '+00:00',
            eventType: 'NOT_A_REAL_TYPE'
          })
        })
      ).rejects.toThrow(/ASSERT_RANGE|range/i);
    });
  });
  ```

  Notes:
  - The `cds.test(...)` call at the top deploys the full project model into in-memory SQLite once per test file (vitest isolates files into separate processes by default).
  - The third test deliberately goes through `AdminService` because `@assert.range` is enforced at the service layer, not the database layer — a raw `INSERT.into(Events)` via the persistence service skips the guard and is the wrong place to assert this.
  - Test data uses synthetic `evt-*-test-*` IDs and `legacyId` values in the 990000+ band to stay out of any seed-CSV collision range.
