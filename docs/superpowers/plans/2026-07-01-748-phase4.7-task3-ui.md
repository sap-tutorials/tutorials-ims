**PR title:** stacks onto the existing single PR (no new PR).

**Goal:** Make help-docs user-visible. Concept landing pages get a **NEW section #3** "Docs explaining this concept" — the first mid-list insert in the phase-4 sequence (existing sections #3-#8 shift down one slot). Tutorial-OP sidebar's `otherResources` widens to render a `help-doc` row type alongside the existing 6 (compact `<badge> Title ↗` shape, tight one-line). `scripts/fetch-concepts.ts` emits per-concept `helpDocs[]` into Hugo frontmatter. **Prerequisites:** Tasks 1 and 2 merged and deployed. `/build/concepts` payload already returns `helpDocs[]` with `sourceLabel` + `anchorLabel` + `snippet` pre-computed (Task 2). Neighborhood enrichment already returns help-doc rows via the 7-array merge in `srv/lib/kg-neighborhood.js`. Read spec §4.7 (payload), §4.8 (UI surfaces — pay close attention to §4.8.1's section-shift note), §8 (telemetry).

**THE BIG THING that makes Task 3 different from Phase 4.1-4.6 Task 3s:** section INSERT at position #3, not append. In every prior sub-phase the new concept-page section slotted between the last content-type section and the `Prerequisites` block at the tail; the `<script>` telemetry IIFE below just grew a new block on the end. Phase 4.7 breaks that pattern:

- The concept page needs the new `<section data-kg-section="help-docs">` block **wedged in between Learning journeys (#2) and Blog posts (previously #3, now #4)**.
- The page-bottom telemetry IIFE has 6 existing blocks (learning-journeys → blog-posts → discovery-missions → videos → api-docs → samples) using `var i / j / k / l / m / n / o` loop counters. The 8th block for help-docs is a new counter (`var p`); position within the IIFE is irrelevant (the blocks are independent `document.querySelector` calls), so we **append** it — matching prior-phase muscle memory. But the concept-page section MARKUP position is not append.

Final section order after Task 3:
1. Tutorials teaching this concept (existing, unchanged position)
2. Learning journeys for this concept (existing, unchanged position)
3. **Docs explaining this concept** ← NEW (Phase 4.7)

```javascript
  for (var p = 0; p < helpDocLinks.length; p++) {
    (function (a) {
      a.addEventListener('click', function () {
        try {
          window.dispatchEvent(new CustomEvent('kg.help-doc.linked_from_concept_page', {
            detail: {
              conceptSlug: helpDocSectionConceptSlug,
              helpDocSlug: a.getAttribute('data-help-doc-slug')
            }
          }));
        } catch (e) { /* never let telemetry break the page */ }
      });
    })(helpDocLinks[p]);
  }
}
```

**Note on the IIFE structure:** each of the 8 blocks is completely self-contained (its own `var section`, own `var links`, own loop counter). The naive alternative — a shared registry of `[selector, event-name, slug-attr]` tuples — was rejected in Phase 4.1 for readability; Phase 4.7 continues that convention.
